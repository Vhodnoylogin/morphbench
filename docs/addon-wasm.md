# WebAssembly inside an add-on

Application **0.8.5** permits a local browser add-on to compile embedded WebAssembly
bytes. The published Application 0.8.0 baseline does not provide this policy.
The module executes inside the add-on's existing opaque-origin sandbox, not in Python,
the host page or the game process. API v1 and independent previews keep their contracts.

## One source, two build targets

An add-on author can compile one portable C/C++ calculation kernel for their native
game plug-in and for WebAssembly. Package the WebAssembly output as base64 data in a
local `.js` file, generated by the author's build. JavaScript marshals arrays, validates
arguments and presents results; the calculation remains in that one kernel. Morphbench
does not supply a compiler, consumer formulas or a native-library bridge.

For a minimal consumer, load an external local script from the package's entry HTML:

```html
<script src="kernel-bytes.js"></script>
<script src="main.js"></script>
```

The generated `kernel-bytes.js` defines `KERNEL_BASE64`. The following loader belongs to
the add-on's `main.js`:

```javascript
async function loadKernel() {
  if (typeof WebAssembly !== "object" ||
      typeof WebAssembly.instantiate !== "function") {
    throw new Error("This browser does not support WebAssembly.");
  }
  const bytes = Uint8Array.from(atob(KERNEL_BASE64), ch => ch.charCodeAt(0));
  // Supply only the imports required by this kernel. No Morphbench/OS import is added.
  const {instance} = await WebAssembly.instantiate(bytes, {});
  return instance.exports;
}

try {
  const kernel = await loadKernel();
  // Validate the expected exports and the kernel ABI before passing user data.
} catch (error) {
  // Show an actionable error. Unsupported browsers/CSP, invalid modules and missing
  // imports fail explicitly; do not silently substitute a second set of formulas.
}
```

Translate the example's visible errors in the add-on. The exact exports, memory layout,
numeric precision, bounds checks and shared native/WASM verification belong to its
author. A successful module instantiation does not prove native/WASM result equivalence.

## Permissions and limits

The host adds only the CSP token **`'wasm-unsafe-eval'`** to add-on `script-src`. It does
not add JavaScript `'unsafe-eval'`. Frames retain `sandbox="allow-scripts"`, without
`allow-same-origin`, and `connect-src 'none'`. Package assets remain generation-pinned;
disabled or superseded packages cannot fetch their scripts through the host.

There is no new SDK RPC. Detect the browser's `WebAssembly` API and handle compile/link
errors. Older hosts can expose the API but still refuse compilation under their CSP;
the instantiation attempt is the final capability check.

The existing package limits apply: by default a ZIP is at most 16 MiB, one decoded
package file at most 4 MiB, and total uncompressed package data at most 16 MiB. Base64
adds roughly one third to module size and counts within the JavaScript file's limit.
These values come from the host's `addonLimits` settings; an add-on cannot override them.

Raw `.wasm` assets are not accepted by this minimal transport. Do not use `fetch`,
`instantiateStreaming`, a CDN, a `blob:` script, a worker or a Windows DLL import. The
compiled bytes must be embedded in an allowed local package script. No new MIME type,
network permission or native binary dependency is introduced into Morphbench.

The sandbox is trust isolation, not a hostile-code or resource-exhaustion guarantee.
WebAssembly can still allocate memory or block its frame. Keep the kernel bounded and
avoid starting long-running computations on the UI thread.

## Qualification

`tests/test_addon_wasm.py` verifies actual local HTTP policy headers, unchanged sandbox
restrictions, package generation/enable checks, rejection of raw WASM assets and the
embedded-byte instantiation pattern using Node when present. Browser CSP enforcement
requires a real browser check; a consumer must also test its own actual compiled kernel.

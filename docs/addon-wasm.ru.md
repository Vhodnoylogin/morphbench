# WebAssembly внутри аддона

Application **0.8.5** позволяет локальному браузерному аддону компилировать встроенные
байты WebAssembly. Опубликованная Application 0.8.0 такой политики не предоставляет.
Модуль исполняется в существующей песочнице аддона с непрозрачным origin, а не в Python,
основной странице или процессе игры. Контракты API v1 и независимых превью сохраняются.

## Один исходник, две цели сборки

Автор аддона может собрать одно переносимое вычислительное ядро C/C++ для своего
нативного игрового плагина и для WebAssembly. Результат WebAssembly следует включить
как данные base64 в локальный файл `.js`, сгенерированный сборкой автора. JavaScript
передаёт массивы, проверяет аргументы и показывает результаты; вычисления остаются в
едином ядре. Morphbench не предоставляет компилятор, формулы потребителя или мост к DLL.

Минимальный потребитель загружает внешние локальные скрипты из входного HTML пакета:

```html
<script src="kernel-bytes.js"></script>
<script src="main.js"></script>
```

Сгенерированный `kernel-bytes.js` определяет `KERNEL_BASE64`. Следующий загрузчик
размещается в `main.js` аддона:

```javascript
async function loadKernel() {
  if (typeof WebAssembly !== "object" ||
      typeof WebAssembly.instantiate !== "function") {
    throw new Error("Этот браузер не поддерживает WebAssembly.");
  }
  const bytes = Uint8Array.from(atob(KERNEL_BASE64), ch => ch.charCodeAt(0));
  // Передавайте только импорты этого ядра. Импорты Morphbench/ОС не добавляются.
  const {instance} = await WebAssembly.instantiate(bytes, {});
  return instance.exports;
}

try {
  const kernel = await loadKernel();
  // До передачи пользовательских данных проверьте ожидаемые экспорты и ABI ядра.
} catch (error) {
  // Покажите понятную ошибку. Неподдерживаемый браузер/CSP, неверный модуль и
  // отсутствующие импорты дают явный отказ; не подменяйте их вторым набором формул.
}
```

Переведите видимые ошибки примера средствами аддона. Экспорты, раскладка памяти,
точность чисел, проверка границ и совместная проверка native/WASM относятся к обязанностям
его автора. Успешное создание экземпляра модуля не доказывает равенство результатов native/WASM.

## Разрешения и ограничения

Хост добавляет к `script-src` аддона только CSP-токен **`'wasm-unsafe-eval'`**.
JavaScript `'unsafe-eval'` не добавляется. У фреймов остаются `sandbox="allow-scripts"`,
отсутствие `allow-same-origin` и `connect-src 'none'`. Пути ресурсов по-прежнему привязаны
к поколению пакета; скрипты отключённых или заменённых пакетов через хост недоступны.

Нового SDK RPC нет. Проверяйте наличие браузерного API `WebAssembly` и обрабатывайте
ошибки компиляции/связывания. Старый хост может иметь API, но запрещать компиляцию своей
CSP; окончательная проверка возможности — попытка создания экземпляра.

Действуют существующие лимиты пакетов: по умолчанию ZIP до 16 МиБ, один распакованный
файл до 4 МиБ, все распакованные данные до 16 МиБ. Base64 увеличивает размер модуля
примерно на треть и учитывается в лимите JavaScript-файла. Эти значения определяют
настройки хоста `addonLimits`; аддон не может изменить их.

Необработанные ресурсы `.wasm` этим минимальным способом передачи не принимаются.
Не используйте `fetch`, `instantiateStreaming`, CDN, `blob:`-скрипты, worker или импорт
Windows DLL. Скомпилированные байты должны быть встроены в разрешённый локальный скрипт
пакета. Новые MIME-типы, сетевые разрешения или нативные зависимости в Morphbench не вводятся.

Песочница обеспечивает разделение доверия, но не гарантирует защиту от вредоносного кода
или исчерпания ресурсов. WebAssembly всё ещё может выделять память или блокировать
фрейм. Ограничивайте вычисления ядра и не запускайте длительную работу в потоке UI.

## Проверка

`tests/test_addon_wasm.py` проверяет заголовки реального локального HTTP, сохранение
ограничений песочницы, поколение/активацию пакета, отказ от сырых WASM-ресурсов и создание
экземпляра из встроенных байтов через Node при его наличии. Применение CSP проверяется
в настоящем браузере; потребитель также должен проверить своё скомпилированное ядро.

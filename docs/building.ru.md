# Сборка morphbench

BodySlide собирает тело — morphbench его проверяет: читает собранное и говорит, держатся ли
морфы, шары охвата и капсулы столкновений. Вне игры, за секунды. Эта страница — для того,
кто собирает окно запуска `morphbench.exe` и пакует верстак. Раздельные выпуски используют
проверенный Runtime и поставляют изменения Application отдельно. Рецепт прежнего полного
архива остаётся доступен.

Чтобы просто пользоваться верстаком из рабочей копии, эта страница не нужна: всё необходимое —
в [quickstart.ru.md](quickstart.ru.md). Что это за инструмент и как он устроен — в
[../README.ru.md](../README.ru.md).

## Продукты сборки

| Продукт | Из чего | Чем | Куда ложится |
|---|---|---|---|
| `morphbench.exe` | `launcher/morphbench.cs` + `launcher/morphbench.manifest` + `launcher/morphbench.ico` | `launcher/build.cmd` | рядом с `mb.py`, в корень модуля |
| `launcher/morphbench.ico` | два десятка чисел в `launcher/make-icon.py` | `python launcher/make-icon.py` | `launcher/morphbench.ico` (версионируется, см. ниже) |
| `morphbench-<версия>.zip` | сам модуль плюс уложенные внутрь зависимости | `python release.py` | `build/` |
| `morphbench-runtime-<версия-runtime>-win64.zip` | файлы Runtime из полной папки существующего выпуска, без изменения байтов | `python release.py --package runtime` | папка `--out` |
| `morphbench-application-<версия>.zip` | исходники и файлы Application с привязкой к манифесту Runtime | `python release.py --package application` | папка `--out` |

`morphbench.exe` и ZIP-архивы — продукты сборки, названные в `.gitignore`, и git их не хранит.
Значок — исключение, объяснённое в разделе [Значок](#значок).

## Что нужно на машине сборщика

| Для чего | Что нужно | Примечание |
|---|---|---|
| `morphbench.exe` | ставить нечего | компилятор .NET Framework 4 идёт в составе Windows |
| перерисовать значок | Python с `pillow` | только если `.ico` пропал; обычно он приходит из репозитория |
| полный архив выпуска | Python 3.12+, `pip`, сеть | `pip` притащит `numpy` и `pillow`, из сети придёт встраиваемый Python |
| полный архив выпуска | папка аддона **PyNifly** на диске | находится сама среди аддонов Blender либо задаётся ключом `--pynifly` |
| раздельные пакеты | Python 3.12+ и полная папка существующего выпуска | упаковка Runtime использует её файлы; упаковка Application читает манифест Runtime. Оба шага не скачивают зависимости |
| проверки | Python 3.12+ с `numpy`; `pillow` и PyNifly необязательны | наборы, которым не хватает нужного, пропускают себя сами |

Сам Blender не нужен ни для чего. Верстак не обращается к `bpy`; ему нужна папка аддона, а она
просто обычно лежит среди аддонов Blender.

## morphbench.exe

Одна команда, откуда угодно:

```
launcher\build.cmd
```

Она компилирует `launcher/morphbench.cs` штатным компилятором .NET Framework 4 и кладёт
`morphbench.exe` в корень модуля, рядом с `mb.py`. Ни SDK ставить, ни файла проекта заводить,
ни NuGet тянуть не нужно: `csc.exe` входит в Windows со времён .NET Framework 4, и окно нарочно
написано так, чтобы не требовать ничего новее — тогда это останется правдой и дальше.

Компилятор ищется сперва по пути `%WINDIR%\Microsoft.NET\Framework64\v4.0.30319\csc.exe`, затем
по 32-разрядному `Framework\v4.0.30319\csc.exe`. Коды возврата стоит знать, если сборка встроена
во что-то ещё:

| Код | Что значит |
|---|---|
| 0 | собрано; путь напечатан |
| 2 | `csc.exe` из .NET Framework 4 не найден |
| 3 | значка не было, и `make-icon.py` не смог его нарисовать |
| прочее | собственный код возврата компилятора |

Ключей немного, и каждый на своём месте:

| Ключ | Зачем |
|---|---|
| `/target:winexe` | окно, а не консоль — иначе позади него мигает чёрный ящик |
| `/platform:anycpu` | окно поднимается на той разрядности Windows, куда попало |
| `/codepage:65001` | исходник в UTF-8; без этого компилятор прочтёт его в ANSI-кодировке машины |
| `/win32manifest` | осведомлённость о DPI и Common Controls v6: окно не мыльное и не из 1999 года |
| `/win32icon` | значок **файла**: проводник, панель задач |
| `/resource …,morphbench.ico` | тот же значок **внутри** самого exe: окно WinForms иначе рисует свой стандартный, поэтому код читает этот ресурс и ставит его |
| `/r:System.Windows.Forms.dll`, `/r:System.Drawing.dll` | само окно |
| `/r:System.Web.Extensions.dll` | чтение JSON, которым сервер отвечает на `serve --status` |

Две мелочи про сам `build.cmd`, похожие на придирки, но это не придирки. Файл строго в ASCII,
а концы строк в нём — CRLF; для всех машин это закреплено строкой `*.cmd text eol=crlf`
в `.gitattributes`. `cmd.exe` читает командный файл в консольной кодировке и держит место в нём
по смещению в байтах: один посторонний не-ASCII байт или концы строк LF — и он начинает выполнять
обрывки строк. Отказ при этом молчаливый и выглядит как что угодно, только не как беда
с кодировкой.

**Что нужно готовому окну при запуске.** Своего Python оно не запускает, поэтому тексты читает
прямо из `locale/<язык>/*.json`, а чтобы было что запускать, рядом должен лежать `mb.py`. Модуль
оно ищет в папке, переданной аргументом, затем по `MORPHBENCH_HOME`, затем в своей собственной
папке, затем в текущем каталоге. Держи exe в корне модуля — и ничего из этого не понадобится.
Как устроены тексты — в [localisation.ru.md](localisation.ru.md).

## Значок

Значок рисуется скриптом, а не хранится картинкой, которую кто-то когда-то сделал:

```
python launcher/make-icon.py --show
```

Он пишет `launcher/morphbench.ico` из семи слоёв (от 16 до 256 точек), а с ключом `--show` кладёт
рядом ещё и `.png` на 256 точек — его уже можно открыть и посмотреть глазами. На 24 точках
и мельче рисуется упрощённый вариант: диагональ сетки на таком размере тоньше линии и сливается
в кляксу. Ради этого слои и рисуются порознь, а Pillow получает их через `append_images`; без
этого Pillow сожмёт одну картинку до всех размеров, и упрощённый слой до файла не доедет.

Сюжет — узлы сетки, один из которых отведён в сторону и покрашен. Это не украшение: верстак
работает с **любыми** морфами, а морф — это и есть смещение вершины. Значок со зверем обещал бы
инструмент для одного существа, которого здесь нет.

**`.ico` версионируется, через Git LFS** — одной строкой в `.gitattributes`:

```
*.ico filter=lfs diff=lfs merge=lfs -text
```

Внутрь `morphbench.exe` попадают ровно эти байты, поэтому воспроизводимым должен быть именно
файл, а LFS держит двоичное вне истории коммитов, где оно всё равно показывало бы только
«файл изменился». Превью `.png` — побочный продукт, и оно игнорируется.

Тут есть ловушка. Клонирование без установленного git-lfs даёт вместо значка `morphbench.ico`
маленький текстовый указатель. `build.cmd` перерисовывает значок только тогда, когда файла
**нет**, поэтому он отдаст указатель компилятору и сборка упадёт на нечитаемом значке. Лечится
это командой `git lfs pull` либо удалением файла — тогда `make-icon.py` нарисует его заново,
но для этого нужен `pillow`.

Комментарий в шапке `build.cmd` до сих пор утверждает, что значок не версионируется. Комментарий
устарел; правило задают `.gitattributes` и `.gitignore`.

## Раздельные пакеты Runtime и Application

Установка сохраняет плоскую раскладку: `morphbench.exe`, `mb.py`, `python/`, `vendor/`,
`launcher/` и папки Application находятся в одном корне. Поэтому прежние пути лаунчера
и MO2 остаются рабочими. Упаковка Runtime копирует существующие байты лаунчера, а не
компилирует новый exe.

Сначала выберите полную папку существующего выпуска с лаунчером, встроенным Python,
зависимостями vendor, исходниками пересборки лаунчера и сведениями о лицензиях. Упакуйте Runtime:

```
python release.py --package runtime --runtime-from "<complete-release-folder>" --runtime-version 1 --out "<builds>"
```

Будет создан `morphbench-runtime-1-win64.zip`. Манифест `runtime-manifest.json` в папке
раскладки содержит идентификатор Runtime `runtime-1-win64`, список его файлов с SHA-256
и `contentHash` этого списка. Путь к манифесту в раскладке, напечатанный сборщиком,
используется в следующей команде:

```
python release.py --package application --runtime "<runtime-stage>/runtime-manifest.json" --version 0.8.0 --out "<builds>"
```

Будут созданы `morphbench-application-0.8.0.zip` и `application-manifest.json` в раскладке.
Манифест Application записывает её версию, список принадлежащих ей файлов и точные
требуемые идентификатор и хеш содержимого Runtime. Версия Runtime `1` независима от версии
Application `0.8.0`; похожее имя или та же версия Python не заменяют закреплённый хеш.

| Пакет | Содержимое |
|---|---|
| Runtime | `morphbench.exe`, `python/`, `vendor/`, исходники пересборки лаунчера и сведения о лицензиях сторонних компонентов |
| Application | `mb.py`, `mb_distribution.py`, `update.py`, `morphbench/`, `presenters/`, `web/`, `locale/`, `docs/`, документация выпуска и лицензии |

Пакеты Application исключают нативные `.exe`, `.dll`, `.pyd` и `.so`, папки Runtime
`python/`, `vendor/`, `launcher/`, настройки машины, установленные дополнения, тесты,
кеши и вложенные архивы. В них находятся исходники Python и JavaScript, которые всё равно
являются исполняемым кодом. Принадлежность файлов задаёт список пакета; обновлятор
не определяет её по имени папки.

Для первой установки содержимое **обоих** архивов распаковывают в одну новую папку,
объединяя содержимое внешних папок с разными именами. Следующие обновления Application
выполняют через `update.py` после остановки сервера. Блокировка установки не допускает
одновременной работы Application и обновлятора в одной установке. Манифесты и хеши Runtime
проверяются до импорта нативных модулей; рабочие копии исходников без манифестов выпуска
по-прежнему запускаются. Точные шаги установки, проверки, обновления, восстановления
и перехода описаны в [updating.ru.md](updating.ru.md).

Проверяйте и выпускайте Runtime отдельно. Любое изменение его зависимостей, обновление
безопасности или пересборка лаунчера требуют новой проверки Runtime и соответствующего
манифеста; обновления одной Application не могут заменять эти файлы. Повторное использование
тех же байтов исключает ненужные изменения нативных файлов, но постоянные хеши не гарантируют
одобрения антивирусами или Nexus. Установка и обновления не предоставляют автоматической загрузки.

## Прежний полный архив выпуска

По умолчанию по-прежнему выбран `--package full`. Старые команды полного выпуска сохраняют поведение:

```
python release.py --version 0.7.0
```

Эта команда раскладывает `build/morphbench-0.7.0/` и пакует её в `build/morphbench-0.7.0.zip`.
Папка раскладки на каждом запуске **удаляется и создаётся заново**, так что ничего своего внутри
оставлять нельзя.

Прежде чем что-то собирать, полезно спросить, что войдёт:

```
python release.py --list
```

Он печатает все наши файлы, подошедшие под перечень содержимого, их число и по строке на каждую
зависимость: идёт ли она внутрь и куда. Ничего при этом не собирается.

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `--version X` | `0.0.0` | номер в имени папки, в имени архива и в `manifest.json` |
| `--out <папка>` | `build` | куда лягут папка раскладки и архив |
| `--pynifly <папка>` | ищется сам | взять аддон отсюда, а не искать |
| `--python-version X` | `3.12.8` | какой встраиваемый Python скачать |
| `--no-python` | — | без встроенного Python: у пользователя должен быть свой |
| `--no-vendor` | — | вообще без чужого кода — один верстак |
| `--stage-only` | — | разложить папку и не паковать |
| `--list` | — | сказать, что войдёт, и остановиться |

`--stage-only` — тот ключ, которым пользуются, пока правят сам выпуск: папку можно осмотреть,
запустить и выбросить, не дожидаясь каждый раз архива.

`release.py` не импортирует из верстака ничего — даже его каталог сообщений. Так сделано нарочно:
выпуск должен собираться на машине, где зависимости ещё не поставлены и сам верстак не запустился
бы. Свои тексты он читает одной стандартной библиотекой из `locale/<язык>/release.json`, а язык
берёт из `MORPHBENCH_LANG`, потому что угадывать язык машины — работа каталога, а тот, кто
собирает выпуск, может просто сказать.

Сам `release.py` внутрь собранного архива не попадает никогда. Он принадлежит репозиторию,
а не выпуску.

### CONTENT: что входит в полный архив

Содержимое архива заявлено в одном месте — списком `CONTENT` в начале `release.py`, — и заявлено
**перечислением**:

```
python release.py --list
```

| Образец | Что несёт |
|---|---|
| `mb.py`, `mb_distribution.py`, `update.py` | командная строка, проверка выпуска и локальное обновление |
| `morphbench.exe` | окно запуска — собери его *до* выпуска, само оно не соберётся |
| `LICENSE`, `README.md`, `README.ru.md`, `dependencies.json` | лицензия, витрина на обоих языках, заявление о зависимостях |
| `CHANGELOG.md`, `CHANGELOG.ru.md` | история выпусков на обоих языках |
| `morphbench/*.py`, `presenters/*.py` | ядро и слои показа |
| `locale/*/*.json` | все рабочие разделы всех языков; нужный только сборщику `release.json` исключается |
| `web/*.html`, `web/*.css`, `web/js/*.js` | страница-смотрелка |
| `docs/*.md` | эта документация, оба языка |
| `launcher/*.cs`, `launcher/*.cmd`, `launcher/*.py`, `launcher/*.manifest`, `launcher/*.ico` | полные исходники, сценарий сборки и ресурсы скомпилированного окна запуска |

Исходники окна остаются рядом с двоичным файлом, чтобы и в зеркальной копии архива были все
входные файлы для его пересборки. Рабочий Python-код уже является исходниками и не заменяется
скомпилированными файлами.

Инструкции разработчикам (`CLAUDE.md`, `AGENTS.md`, `SKILL.md`) остаются в репозитории исходников.
Они исключаются, даже если находятся в папке, выбранной образцом содержимого.

Всё, что там не названо, в архив попасть не может, сколько бы его ни лежало рядом в рабочей
копии. Ради этого правило и повёрнуто именно так: репозиторий — одна рабочая копия с несколькими
модулями, и плагин-мост к MO2 лежит в соседней папке. Список исключений пришлось бы дописывать
при появлении каждого нового соседа — и однажды тихо не дописать. Список включений ошибается
в другую сторону: пропадает что-то наше, и `--list` показывает это сразу.

Дальше `SKIP` отбрасывает четыре вещи, которые под образцы всё-таки подходят: `__pycache__`,
`.pyc` и два файла, оставшихся от запуска, — `morphbench.json` и `morphbench.log`. Настройки
и журнал принадлежат машине, а не выпуску.

Также исключается каталог текстов `release.json` каждого языка: им пользуется только
`release.py`, а сборщик остаётся в репозитории. Исходный каталог по-прежнему доступен сборщику.

Два следствия, о которых стоит помнить, добавляя файлы:

* **Образцы работают на один уровень вглубь.** `web/js/*.js` подхватит новый скрипт в `web/js/`
  сам — порядок загрузки для него объявляется в `PageAssets.SCRIPTS`, а не здесь, — но новой
  папке, скажем `web/img/`, нужна новая строка в `CONTENT`, иначе она молча не поедет. То же
  и с новым подпакетом внутри `morphbench/`.
* **Новый язык и новый рабочий раздел едут сами.** `locale/*/*.json` покрывает и то и другое; ради этого
  язык и сделан папкой файлов-разделов, а не одним большим файлом — см.
  [localisation.ru.md](localisation.ru.md).

### Что оказывается в папке раскладки

Кроме наших собственных файлов туда пишутся три вещи, которых в репозитории нет:

| Что | Кем | Содержимое |
|---|---|---|
| `vendor/`, `python/`, `vendor/io_scene_nifly/` | шагами укладки | всё чужое, разложенное там, где его ждёт верстак |
| `THIRD-PARTY.md` | `third_party()` | перечень чужой работы с лицензиями и адресами исходников |
| `manifest.json` | `main()` | имя, версия, лицензия, какой Python уложен, какие зависимости вошли |

## dependencies.json: что кладётся внутрь и почему

`dependencies.json` пишет человек. Это **заявление** о зависимостях, а не их копия: по нему
`release.py` собирает архив и по нему же пишет `THIRD-PARTY.md`.

| Имя | Что это | Лицензия | Внутрь? | Куда | Зачем нужно |
|---|---|---|---|---|---|
| Python 3.12+ | среда исполнения | PSF-2.0 | да | `python/` | на нём написан весь верстак |
| numpy | пакет | BSD-3-Clause | да | `vendor/` | вся арифметика по вершинам: морфы, растяжение, охват, капсулы |
| pillow | пакет | MIT-CMU | да | `vendor/` | запись кадров в PNG; без него работает всё остальное, страница в том числе |
| PyNifly | папка аддона | GPL-3.0 | да | `vendor/io_scene_nifly` | чтение и запись NIF и файлов морфов TRI/TRIP |

**Решает лицензия, а не удобство.** PyNifly под GPL-3, как и мы, поэтому его можно и нужно везти
внутри; numpy, pillow и Python — под лицензиями, которые раздачу дальше разрешают. Зависимость,
которую внутрь класть нельзя по закону, помечается `bundle: false`, и тогда её запись обязана
сказать, где пользователю её взять. Сегодня так не помечено ничто:
пара Runtime/Application и прежний полный архив содержат нужные зависимости.

Поля записи описаны блоком `note` в начале файла. Два стоит повторить здесь. `why` говорит, зачем
верстаку эта вещь, и **запись без него заводить нельзя**: зависимость, которую некому оправдать, —
это зависимость, которую никто не решится убрать. `proof` перечисляет файлы, обязанные лежать
внутри папки, чтобы вместо нужной не подхватилась чужая папка с тем же именем: для PyNifly это
`pyn/pynifly.py`, `NiflyDLL.dll`, `tri/trifile.py` и `tri/tripfile.py`. Каждый проверочный путь
должен быть файлом. Указать ключом `--pynifly` не ту папку —
сборка остановится и скажет, каких файлов не хватило, вместо того чтобы упаковать чужой код.

Список `search` — то место, где сборка смотрит на машину сборщика: папки аддонов и расширений
Blender под `%APPDATA%` и `%LOCALAPPDATA%`, затем `./vendor/io_scene_nifly` в рабочей копии.
`%VARIABLE%` берётся из окружения, `*` ведёт себя как в имени файла. Кандидаты перебираются
в обратном порядке имён, поэтому выигрывает самая новая версия Blender.

Список `keep` PyNifly переносит рабочее дерево `pyn/`, `NiflyDLL.dll` и только два файла
разбора `tri/trifile.py` и `tri/tripfile.py`. Вложенные файловые записи сохраняют относительные
пути; сборщик создаёт родительские папки. Morphbench загружает эти файлы напрямую, потому что
инициализатор пакета `tri` импортирует Blender. Папка `nif/` и модули интерфейса TRI для Blender
не используются и в выпуск не входят. Чужие исходные файлы копируются без правок.

### Пакеты и встраиваемый Python

`numpy` и `pillow` ставятся тем же `pip`, который и так есть, но не в систему, а в папку выпуска:
`pip install --target <раскладка>/vendor`. Из копии для выпуска удаляются папки зависимостей
`test`/`tests`, `__pycache__`, кеши `.pyc`, описания типов `.pyi` и служебные файлы сборки
NumPy `_pyinstaller`, а также созданные pip утилиты сборки `f2py.exe`/`numpy-config.exe`.
Также удаляются заголовки NumPy `_core/include/`, статические и импортные библиотеки `.lib`
и настройки сборки `_core/lib/pkgconfig/`. Рабочие расширения `.pyd` и DLL остаются, как и
импортируемые API, например `numpy.testing`, `numpy.typing` и `numpy.f2py`.
`.dist-info` остаётся вместе с точными версиями пакетов и файлами лицензий; `RECORD` перечисляет
только сохранённые файлы. Установленные на машине сборщика зависимости не изменяются.

Отсюда следует правило, на котором легко споткнуться: **запускать `release.py` надо на той же
основной и младшей версии Python, которая укладывается внутрь, на 64-битном Windows.**
Сборщик проверяет это до раскладки. `pip --target` подбирает wheel-пакеты под тот
интерпретатор, который его запустил, так что сборка на 3.13 при встраиваемом 3.12 положит
скомпилированные расширения, которые уложенный интерпретатор не сможет импортировать.

Встраиваемая сборка Python скачивается прямо с python.org — это архив без установщика, который
просто распаковывается. Она нарочно сделана слепой: по сторонам не смотрит, и `vendor/` вместе
с папкой верстака были бы для неё невидимы. `release.py` переписывает файл `python*._pth`,
добавляя `..` и `..\vendor` и включая `import site`. Строку при этом надо именно **заменить**,
а не дописать рядом: в готовой сборке `import site` закомментирован, и новая строка рядом
с закомментированной оставляет старую на месте, а пути так и не подхватываются.

Стандартная библиотека из `python312.zip` распаковывается без изменения файлов в
`python/python312/`, а запись `_pth` указывает на эту папку. Вложенного ZIP с Python
в выпуске нет. Файлы `.pyc` стандартной библиотеки — необходимый для работы байткод;
они сохраняются и отличаются от временных кешей зависимостей. Такая раскладка позволяет
проверять содержимое согласно правилу Nexus о вложенных архивах, но не означает одобрения
антивирусами или модератором.

### THIRD-PARTY.md

GPL требует, чтобы перечень чужой работы ехал вместе с двоичным, и `release.py` пишет его
в полный выпуск из `dependencies.json` и сохраняет при упаковке Runtime: на каждую запись —
что это, зачем оно верстаку, лежит ли внутри пакета и где, под какой лицензией и где живут
её исходники. `NiflyDLL.dll`
скомпилирован; общий адрес исходников сам по себе не определяет точные входные данные
сборки конкретного двоичного файла.

Все 27 файлов PyNifly в проверенном пакете 0.8.0 совпадают с авторским
[выпуском V28.1.0](https://github.com/BadDogSkyrim/PyNifly/releases/tag/V28.1.0).
Его 26 файлов без DLL также совпадают с
[коммитом 934fbbf](https://github.com/BadDogSkyrim/PyNifly/tree/934fbbfbb41b63ed636d44afa957ec98d7fb0803).
Проект upstream ссылается на отдельную соседнюю библиотеку Nifly без точной ревизии её
сборки. Проверка устанавливает происхождение файлов выпуска; воспроизводимость сборки DLL
и полное происхождение исходников её нативных зависимостей не установлены.

Переводится только рама этого документа. Записи копируются из `dependencies.json` слово в слово,
а тот файл — на английском.

Исходникам самого morphbench отдельный шаг не нужен: архив везёт тот же Python, который
и выполняется. Об этом и говорит заключительный раздел `THIRD-PARTY.md`.

## Прогон проверок

```
python tests/run.py
```

По одному набору за раз, по образцу имени файла:

```
python tests/run.py test_physics.py
```

Любой файл проверок запускается и сам по себе:

```
python tests/test_colliders.py
```

Только `unittest` из стандартной библиотеки — стороннего фреймворка проверок ставить не надо.
Сами проверки лежат вне пакета `morphbench/` и им не импортируются; корень модуля они находят
от собственного расположения.

Три вещи про прогон:

* **Язык закреплён.** `run.py` и `common.py` оба выставляют `MORPHBENCH_LANG=en`, потому что
  часть проверок сверяет тексты сообщений слово в слово и иначе у одного человека проходила бы,
  а у другого падала. Выставляется через `setdefault`, поэтому прогон, который намеренно просит
  снаружи другой язык, его сохранит.
* **Ни одна проверка не читает файл из сборки модов.** Тела собираются в памяти из нескольких
  десятков вершин и подключаются к фасаду через `MorphBench.attach`; настройки создаются
  во временной папке, поэтому настоящий `morphbench.json` не трогается. Значит, падение проверки
  означает поломку ядра, а не то, что какой-то меш изменился.
* **Пропуск — не отказ.** Наборам, которым нужно записать настоящий `.nif` или `.tri`, нужен
  PyNifly, и без него они пропускают себя, назвав причину. Так же ведут себя `pillow` и модуль
  сервера. Какому набору что нужно — сведено в [../tests/README.ru.md](../tests/README.ru.md).

Прогон заканчивается одной итоговой строкой — наборы, сломанные наборы, проверки, падения, ошибки,
пропуски — и выходит с кодом 1, если что-то упало или ошиблось, так что его можно встроить
во что-то ещё.

Проверок в `CONTENT` нет: они остаются в репозитории и в выпуск не едут.

## Шероховатости, названные прямо

Они настоящие, и в коде всё именно так.

* **Нигде не записано, что готовый архив распаковывали и запускали на машине без Python
  и без Blender.** Самодостаточность — это замысел; первый собранный архив стоит считать тем,
  что надо проверить, а не тем, что можно раздавать.

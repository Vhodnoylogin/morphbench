# morphbench — верстак для морфов

Программа для работы с телами и именованными морфами Skyrim вне игры: прочитать меш, посмотреть
привязки вершин к костям, измерить каждый ползунок, применить набор значений и получить
изображение — не запуская ни игру, ни Blender, ни оконный редактор.

Кто хочет **пользоваться** верстаком, а не дописывать его, начинает с
[docs/quickstart.md](docs/quickstart.md): требования, запуск, команды, настройки и на что
смотреть в ответах. Ниже — устройство и правила, по которым он написан.

Задача, ради которой она заведена, — **сократить время между гипотезой и её проверкой**. Пока
единственным способом увидеть морф был игровой прогон, каждая догадка стоила запуска игры,
живого человека в шлеме и описания словами. Всё, что можно увидеть без игры, должно быть видно
без игры.

## Устройство: ядро без визуала, показ поверх

Программа разделена на два уровня, и граница между ними жёсткая.

**Ядро** (`morphbench\`) — объектное, техническое и **полностью лишённое визуала**. Оно не
рисует, не открывает окон, не собирает страниц и не знает слова «пиксель». Оно загружает меши
и морфы, считает, измеряет и хранит состояние. Разговаривает числами.

**Слои показа** (`presenters\`) — надстройки поверх готового ядра. Каждая берёт у ядра числа
и превращает их во что-то видимое: таблицу в консоли, машинный JSON, картинку PNG, страницу
в браузере. Ни одна из них ничего не вычисляет сама, и ядро о них не знает.

Отсюда главное правило границы: **любое действие, которое умеет интерфейс, обязано быть вызовом
метода ядра.** API здесь — это набор методов интерфейса внутри самой программы, а не веб-служба.
Повернуть камеру, включить слой, потянуть ползунок, покрасить вершины по костям, навести камеру
на лапу — всё это методы `MorphBench`, а кнопка окна лишь зовёт их. Проверить это правило легко:
если действие нельзя выполнить из командной строки, граница проведена неверно.

Побочная выгода прямая и ради неё всё и делается: то, чем можно управлять без окон, может делать
и чат — без человека, без экрана и без игры.

## Команды

    python mb.py summary <меш.nif>                          что открыто
    python mb.py shapes | bones | morphs | empty <меш.nif>  состав меша и ползунков
    python mb.py missing <меш.nif> CLAWNeck ...             каких ожидаемых ползунков нет в файле
    python mb.py strain  <меш.nif> [--morph X]              где морф рвёт поверхность
    python mb.py strain  <меш.nif> --slider A=1 --slider B=1   то же при НАБОРЕ ползунков
    python mb.py strain  <меш.nif> --pairs [--top N] [--by gain]  перебор пар: какие два рвут вместе
    python mb.py budget  <меш.nif> [--threshold X]          бюджет амплитуд: где каждый ползунок переходит порог
    python mb.py layers  <меш.nif> --morph X [--adjacent]   следуют ли оболочки за кожей
    python mb.py binding <меш.nif> --shape body --morph X   к каким костям привязано то, что он двигает
    python mb.py focus   <меш.nif> [--bone B|--morph X|--shape S]   наведение камеры числами
    python mb.py bounds  <меш.nif> [--shape S] [--write новый.nif]  шары охвата: в файле, нужный, перебор
    python mb.py colliders <меш.nif> --skeleton S.nif [--clearance]  капсулы столкновений скелета
    python mb.py fit     <меш.nif> --skeleton S.nif [--bundle N --split axis|kmeans] [--save новый.nif] [--ppb]
                                                            посадить их по коже: одной капсулой или связкой
    python mb.py chains  <меш.nif> --skeleton S.nif [--engine smp|cbpc] [--assign tail=smp,ear=cbpc]
                                                            цепочки для качающейся физики: кожа по звеньям, кому отдана
    python mb.py physics <меш.nif> --skeleton S.nif --engine smp|cbpc [--assign ...] [--out файл]
                                                            настройки качающей физики одного движка его форматом
    python mb.py physics <меш.nif> --skeleton S.nif --engine smp|cbpc --check файл
                                                            готовый файл против скелета и меша; код 3 - есть находки
    python mb.py render  <меш.nif> --out кадр.png [...]     кадр в PNG
    python mb.py sheet   <меш.nif> --out папка [...]        несколько ракурсов подряд
    python mb.py web     <меш.nif> --out страница.html [...] смотрелка в браузере, один файл
    python mb.py env                                        под MO2 ли мы и какой корень обзора
    python mb.py catalog [папка] [--all] [--find X]         обзор мешей с подобранными морфами
    python mb.py serve [--root папка] [--port N]            страница со списком мешей на локальном порту;
                                                            без ключей - просто поднять сервер
    python mb.py serve --status | --stop                    жив ли сервер; остановить его

Ко всякой команде подходит `--json`. Файл морфов подбирается рядом с мешем сам (`--tri` задаёт
явно), скелет — тоже (`skeletonFile` из настроек в папке меша; `--skeleton` задаёт явно);
со скелетом `render`, `sheet` и `web` понимают `--colliders` (слой капсул поверх тела)
и `--bumper` (ещё и цилиндр перемещения). У `render`, `sheet` и `web` общие ключи вида:
`--view front` или произвольный ракурс
`--look 40,15`, `--colour bone|morph|strain`, `--morph X`, `--slider X=1`, `--only body,head`,
`--zoom 2`, масштаб к точке `--zoom-at=2,0.4,-0.3`, панорама `--pan 5,-3`, `--size 900x900`,
свет `--light camera|world`, `--light-dir=x,y,z`, `--light-power=a,d,f` и наведение
`--focus-bone "L Finger" | --focus-morph X | --focus-shape head`. Пары чисел с минусом впереди
пишутся через знак равенства: `--pan=-5,3`.

## Что считает ядро

**Пустые и потерянные ползунки.** Морф, который есть в файле и не двигает ни одной вершины
(`empty`), и морф, который ждали по рецепту и не нашли в файле вовсе (`missing`).

**Растяжение рёбер** (`strain`). Если морф двигает вершины ладони и не трогает пальцы, рёбра
между ними растягиваются во столько раз, во сколько разъехались концы. Мера ловит и «перчатку»
на лапе, и разрыв шва, не требуя ни игры, ни глаза.

**Растяжение от набора, пары и бюджет амплитуд.** Дефект бывает свойством сочетания, а не
одного ползунка: на самке `CLAWTorsoBreastSize` даёт на голове 2.07, `CLAWTorsoChestSize` —
0.80, а вместе — 2.72. Поэтому `strain` с `--slider A=1 --slider B=1` меряет **набор**:
смещения складываются, как при последовательном применении морфов (`edge_strain_set`,
`strain_set`), строки те же, что у одиночного разбора, только вместо имени морфа — набор.
`--pairs` перебирает **все сочетания по два** из непустых ползунков (`strain_pairs`): у пары —
наибольшее растяжение и число рёбер сверх порога по всем частям, часть, где оно наибольшее,
и `gain` — на сколько пара хуже худшего из двух одиночных; интересны именно пары с прибавкой,
поэтому `--by gain` ставит их наверх (по умолчанию порядок по растяжению вместе). Рёбра и их
длины в покое считаются один раз на часть (`edge_lengths`), каждая пара — одно сложение
смещений и один промер: 325 пар на теле в 99 тысяч вершин — около двух секунд.
`budget` (`MorphBench.budget`) для каждого ползунка находит **величину, на которой наибольшее
растяжение переходит порог** `strainThreshold`: двоичный поиск в пределах `sliderRange`
с точностью `budgetResolution`; если и на верхнем пределе порог не перейдён, предела нет —
«в пределах не рвёт». Так «амплитуды нарочно раздуты, потом сведём» становится таблицей чисел.

**Оболочки и их смежность** (`layers`). Кожа двигается своим морфом, оболочки шерсти — своими
копиями; если у оболочки амплитуда меньше или её нет, слои разъезжаются. Но голова не обязана
следовать за животом: оболочка **должна** следовать только там, где лежит поверх сдвигаемой
кожи. Для каждой её вершины ищется ближайшая вершина базовой части в пределах `contactRadius`
(считается один раз на пару частей); доля вершин, под которыми кожа сдвинута, — это `contact`,
а `adjacent` — превысила ли она `minContact`. `expectedMax` — на сколько сдвинута кожа прямо
под оболочкой: столько она и должна была уехать. Ключ `--adjacent` оставляет только смежные
оболочки; без него перечисляются все, как раньше. Базовую часть задаёт `--base`: заплатка шва
между двумя оболочками шерсти лежит не на коже, и спрашивать о ней надо относительно той
оболочки, которую она сшивает.

**Привязки** (`binding`). Каким костям принадлежат вершины, которые двигает морф, и какие кости
сдвинуты лишь частично — там поверхность растягивается.

**Наведение камеры** (`focus`). Кадр всегда охватывал модель целиком, и лапу вблизи было не
рассмотреть. Теперь камеру можно навести на кость (точное имя или подстрока: «L Finger» —
все пальцы левой лапы), на область морфа или на часть меша. Ядро хранит цель числами — центр
и радиус сферы, — а слой показа берёт кадр по ней с запасом `focusPadding`.

**Кадр и масштаб к точке.** Центр и полуразмах кадра считает ядро (`framing`): охват видимых
частей с применёнными ползунками в осях камеры, затем наведение и панорама. Поэтому масштаб
к точке под курсором (`zoom_at`) — тоже дело ядра: точка задаётся долями половины меньшей
стороны кадра от центра, и панорама сдвигается ровно так, чтобы эта точка сцены осталась
на месте. Колесо на странице зовёт этот метод; в командной строке то же даёт `--zoom-at`.

**Свет — состояние показа.** Направление на источник и силы света живут в `ViewState`.
Свет либо **за камерой** (по умолчанию): направление задано в осях камеры — вправо, вверх,
к зрителю — и едет вместе с ракурсом, что видно, то и освещено; либо **отдельно**: направление
мировое, как было раньше. Силы: рассеянная, направленная и встречная подсветка с противоположной
стороны, чтобы тень не была слепой. Затенение по нормали вершины (`shading: smooth`) или
по нормали треугольника (`flat`); нормали считает ядро (`vertex_normals`). Растеризатор
и страница светят одной формулой.

**Обзор мешей и запуск под MO2** (`catalog`, `env`, `serve`). `Catalog` обходит корень, находит
`.nif` и подбирает к каждому `.tri` рядом (то же имя либо имя без суффикса веса `_0`/`_1`),
не открывая файлов; `Environment` отвечает, запущены ли мы под Mod Organizer 2 — по библиотеке
usvfs, загруженной в процесс, — и где `Data` игры (из реестра). Какая из установленных игр
управляется MO2, решает то, в чьей `Data` видна папка `meshes`: у настоящей Skyrim меши лежат
в архивах, россыпная папка появляется только сквозь подмену. Проверяется это чтением списка
каталога (`dir_exists`), а не `is_dir()`: виртуальная папка под usvfs на проверку атрибутов
отвечает «нет», а перечислить себя даёт — так и был найден отказ, когда корнем становилась
`Data` соседней Special Edition. Под MO2 корень обзора — `Data`
со всеми модами сборки, и наружу из него выходить нельзя; без MO2 — любая папка. `serve`
поднимает страницу со списком мешей на локальном порту: тело выбирается без перезапуска.

**Сервер поднимается и без корня** (`serve` без ключей): список пуст, папку называют
на странице или запросом `/api/root`. Если сервер на этом адресе уже поднят, второй `serve`
не поднимает ещё один, а отдаёт ему корень и открывает страницу — это `ServerLink`, клиентская
сторона в том же `serve.py`; он отличает наш сервер от чужой программы на том же порту
по подписи в заголовке `Server`; `serve --status` и `serve --stop` спрашивают и останавливают
его, а `/api/shutdown` — тот запрос, которым это делается. Так устроена **точка входа для
MO2**: окно `morphbench.exe` (`launcher\morphbench.cs`, WinForms, собирается
`launcher\build.cmd` штатным `csc.exe` из .NET Framework, без единого пути внутри) —
состояние сервера, папка обзора, кнопки «поднять», «остановить», «открыть страницу»,
журнал. Окно ничего не считает: каждая кнопка — тот же вызов, что у `serve`; адрес и окружение
оно узнаёт у `serve --status --json`, а не из своих умолчаний. Запущенное из MO2, оно поднимает
`python mb.py serve` своим потомком, и тот видит `Data` со всеми модами; сервер, поднятый
окном, уходит вместе с окном, чужой — остаётся.

**Сервер уходит за окном сам** (`serve --parent <номер процесса>`, `WebServer.watch_parent`).
Мирно закрытое окно останавливает его и без этого, но снятое **жёстко** — аварийное завершение,
«Снять задачу», выход из системы — не успевает. Без сторожа оставался бы невидимый процесс:
порт занят, подмена MO2 для него уже устарела, MO2 его больше не считает запущенной программой,
а точка входа идемпотентна — и следующий запуск молча подключился бы именно к нему. Сторож ждёт
номер процесса по-настоящему (`WaitForSingleObject`), а не опросом, и отпускает порт, а не просто
останавливает обслуживание: иначе сервер стал бы чёрной дырой, принимающей соединения без ответа.
Без номера процесса сторожа нет, и `serve` из консоли ведёт себя как прежде.

**Точка входа идемпотентна.** Нажатие «Поднять» — и запуск `morphbench.exe --start` из MO2 —
делает одно и то же независимо от того, поднят сервер или нет: свободно — поднять, поднят —
подключиться и передать корень обзора. Своей ветки решения у окна нет намеренно: оно зовёт
ту же команду `mb.py serve`, и правило живёт в одном месте. Из-под MO2 передаваемый корень —
`Data` игры, которую этот процесс видит сквозь usvfs; сервер, поднятый вне MO2, мешей сборки
не видит, и такая передача отклоняется словами, а не молча.

## Шары охвата: почему деталь моргает

У каждой части меша в файле записан шар - центр и радиус. По нему игра решает, попала ли
часть в поле зрения; собирается он при сборке **по телу в покое**, и морфы его не расширяют.
Деталь, вытянутая ползунком за шар, пропадает, когда шар выходит из кадра, хотя сама она
ещё на экране, - так и выглядел дефект самца из игры.

`bounds` считает для каждой части шар, накрывающий **всё, во что она может превратиться**:
покой, каждый ползунок на максимуме (и на минимуме, если предел ползунков отрицательный),
все разом и «худший набор» для каждой вершины - те ползунки, что уводят её от центра
(`Reach`). Смещения морфов складываются, поэтому самое дальнее положение вершины лежит
в углу куба значений. Центр ищется по прикидочному облаку, а **радиус меряется точно**
(`reach_exact`): на одну вершину действует лишь k её ползунков, и перебираются 2^k углов
по группам вершин с одинаковым набором — на теле это сотни групп по 3–6 ползунков.
Прикидка «по направлению от центра» здесь не годится: два ползунка вместе уводят вершину
дальше, чем любой из них и чем угадывает знак скалярного произведения, — рецензия нашла
на хвосте перебор в 4,5% сверх записанного шара. Вершины, которых трогает больше
`boundsCornerCap` ползунков, меряются прикидкой, и их число выдаётся строкой (`overCap`). Сам шар - наименьший накрывающий с точностью
в доли процента (`enclosing_sphere`: центр сдвигается к самой дальней точке убывающими
шагами, центр из файла участвует как кандидат, хуже начального не выходит). Больше нужного
шар не раздувается: он же служит отсечению невидимого, и лишний запас стоит кадров; запас -
`boundsMargin`, доля перебора, с которой часть считается исправной, - `boundsTolerance`.

Строка ответа: шар в файле, куда тянется геометрия от его центра, перебор в долях, какой
набор виноват (и какой одиночный ползунок), нужный шар. `--write` кладёт исправленные
шары в **новый файл**: шар - поле постоянного размера внутри блока части, то есть правка на
месте, которую `NifPatch` уже умеет (`read_bounds`/`write_bounds`; раскладка блока известна
от версии Bethesda 100, и перед записью шар из байтов сверяется с прочитанным PyNifly).
Запись только расширяет: часть, чей шар уже накрывает всё, не трогается, более широкий шар
не сжимается — широкий шар в файле бывает намеренным (шерсть под качающейся физикой), и ядро
о таких причинах не знает; `--shrink` пишет нужный как есть. Без открытых морфов запись
отказывает: нужный шар без них — шар покоя. Поверх исходного файла — отказ.

## Колайдеры: вторая, невидимая оболочка

У персонажа кроме видимой кожи есть набор невидимых капсул, по одной на кость. Это по ним
игра считает удары и прикосновения — и лежат они не в меше тела, а **в файле скелета**.
Увидеть их иначе нечем: в кадре их нет, а редакторы мешей показывают только кожу.

Верстак читает их из скелета (`skeleton.nif` в папке меша открывается вместе с телом сам,
другой путь даёт `--skeleton`), переводит в те же координаты, где лежат вершины тела, и умеет
три вещи.

**Смотреть.** `--colliders` кладёт капсулы полупрозрачным слоем поверх тела — и в PNG,
и на странице (раздел «Капсулы» появляется, когда скелет открыт). Там, где капсула внутри
тела, она просвечивает сквозь кожу; там, где вылезает наружу, ложится прямо на фон. Слой
не пишет в общий буфер глубины намеренно: иначе он закрыл бы собой то, ради чего его и смотрят.
Цилиндр перемещения (бампер) стоит отдельно и по умолчанию выключен — он вчетверо больше любой
части тела. Включён ли слой — состояние показа (`colliders`, `bumper` в `view_state()`), как
и всё остальное. Капсулы следуют за частями меша (`collidersFollowParts`): кость видна, пока видна
хоть одна часть, для `boneMinVertices` вершин которой она главная (`Shape.held_bones`);
страница решает то же по `heldBones` частей из payload, не спрашивая сервер.

**Мерить.** `colliders --clearance` говорит, какая доля кожи осталась СНАРУЖИ капсулы и как
далеко от неё ушла самая дальняя вершина. Это и есть ответ на вопрос «пройдёт ли рука сквозь
тело, ничего не задев».

**Сажать.** `fit` считает капсулу по облаку точек кожи (`Capsule.fit`): ось — главное
направление облака, радиус — процентиль расстояния до оси (сотня раздула бы капсулу по одной
выпирающей вершине), концы отступают внутрь на радиус. Кому принадлежит вершина, решает часть
меша (`Shape.owned_vertices`): той кости, которая держит её сильнее всех, иначе цепочки — хвост,
пальцы — расплываются: соседние звенья делят одни и те же вершины. Главная кость каждой
вершины считается один раз на часть. Кожа, за которую отвечает тело, — это кожа его кости
и всех костей-потомков без своих тел (`covered_bones`): у пальцев, крутящих костей предплечья
и таза тел нет, а кожа есть, и её столкновения считает ближайшее тело выше по дереву.

**Связкой** (`fit --bundle N --split axis|kmeans`). Одна капсула верна только для вытянутого;
у облака головы или стопы, одинакового во все стороны, главного направления нет — оно
случайно, и капсула выходит колбасой мимо морды или блином. Поэтому облако сначала режется
на куски (`split_points`): `axis` — ломтики равной численности вдоль оси кости, для конечностей;
`kmeans` — сгустки по близости, начатые из точек вдоль той же оси, для головы: череп, морда
и челюсти находятся сами. По каждому куску садится своя капсула (`fit_bundle`), и связка
целиком становится формой того же тела (`CollisionBody.refit`): тело одно, шарниры те же,
число тел не меняется. Границы между капсулами не вылизываются — для удара безразлично,
в какую именно попало; важно, чтобы снаружи не оставалось кожи. На вервольфе голова
с XP32-капсулой оставляла снаружи 66% кожи, связка из 14 — 28%; стопа 98% → 36% тремя ломтиками.

Ради чего это здесь: **тело верстак деформирует сам** и знает каждую вершину при любом наборе
ползунков. Поэтому посадку можно посчитать точно и заранее, а не угадывать её в игре. По чему
садиться, решает состав видимых частей: скрыл шерсть — сядешь по коже, показал — по силуэту.

Результат уходит двумя путями: `--save` пишет новый файл скелета, `--ppb` выдаёт строки
настроек Precision Physic Bodies — тот перечитывает свой файл примерно раз в секунду прямо
во время игры, и капсула переезжает без перезапуска. Строки складывает слой показа
`presenters\ppb.py` из капсул в системе кости (`collider_local`): ядро о PPB не знает,
как не знает и о других чужих файлах.

Запись — через PyNifly, и только через него. Править капсулу на месте он не умеет
(`setBlock` отвечает «NYI Unimplemented function SET of type 19»), зато умеет поставить телу
новую форму: `body.add_shape` с капсулой либо с `bhkListShape` и капсулой на каждый кусок;
прежняя форма уходит из файла, тело, его шарниры и контроллеры остаются теми же блоками.
Круговой оборот скелета вервольфа через PyNifly проверен: 490 блоков → 490, все типы поимённо
те же, ни один блок не изменился по байтам, разница только в строке экспорта заголовка.
Тело помнит, каким прочитано (`changed`), и `save_as` переписывает форму только у изменённых.
Пишется **всегда новый файл**: прочитанный скелет принадлежит чужому моду. Байтами (`NifPatch`)
правится только шар охвата части, который через сеттер PyNifly молча не меняется.

## Качающаяся физика: цепочки и настройки двух движков

Кроме куклы (капсулы в скелете, по которым считают удары) у персонажа есть вторая,
независимая физика — та, что качает висящее, пока он жив: уши, хвост, грудь. Качает она
не геометрию, а **кости**, цепочкой звеньев `TailBone01…05`, и видно это только там, где
к звену привязана кожа. Звено без кожи — обрыв: то, что за ним, качается, а видно этого
не будет; кончик уха из восьми вершин качается как дощечка.

**Что считает ядро** (`chains.py`, `chains` в фасаде). Звено без кожи — не всегда обрыв:
ведущие звенья без кожи — **опора** (их ведёт анимация, от них качается остальное; у 3BBB
это `Breast00`), звено без кожи посреди — **шарнир** (качается невидимо), звенья без кожи
в конце — **хвост** (отбрасываются). Цепочка годится, если в ней два и больше звеньев
и кожа хоть на одном; обрыв — когда кожи нет ни на одном. Родство звеньев — по дереву
скелета и сквозь прослойки вроде `CME`: у ствола может выйти несколько цепочек (пять пальцев
одной лапы, каждая с номером корня в имени), а параллельные кости без общего предка
цепочкой не считаются. Тег в скобках после номера (`NPC Genitals03 [Gen03]`) снимается.
Цепочка узнаётся по имени — общий
ствол и номер в конце — и выстраивается по дереву костей скелета (без скелета — по номеру);
по каждому звену считается, сколько вершин каких частей меша оно держит по-настоящему
(главная кость вершины, как у посадки капсул). Отсюда обрыв (первое звено с кожей меньше
`boneMinVertices`) и вердикт «годится». Капсулу по коже каждого звена, в системе этой кости,
даёт `chain_capsules`: тем же `Capsule.fit`, что и `fit`, только никуда не применяя — звенья
цепочек своих тел в скелете обычно не имеют, это замер, а не правка.

**Два движка — не два вида одного.** В сборке качают `Faster HDT-SMP` и `CBPC`, и одну кость
обоим отдавать нельзя: они будут тянуть её врозь. Поэтому у цепочки есть **назначение**:
`chainEngines` в настройках — подстрока ствола → `smp` или `cbpc` (`"tail": "smp"`), на один
запуск его меняет `--assign tail=smp,ear=cbpc` (`assign_chains`, файл настроек не трогается).
Цепочка без назначения ни в какой вывод не попадает. Слой показа одного движка
(`physics --engine smp|cbpc`) пишет **только его** цепочки, а в шапке перечисляет всех:
кто отдан ему, кто другому, кто никому и у кого кожи нет вовсе. Молча написать обе
он не может.

**Что складывают слои.** Ядро о форматах не знает — в настройках лежат только числа
(`smp*`, `cbpc*`: массы, затухания, жёсткости, пределы), а в какие строки и теги они
ложатся, решает слой:

- `presenters\smp.py` — XML `hdtSkinnedMeshConfigs`: `<bone name>` с массой, инерцией
  и затуханием на каждое звено (масса легчает к кончику множителем `smpMassTaper`),
  `<generic-constraint bodyA=звено bodyB=родитель>` с пределами и жёсткостью между соседями,
  опора — кость без тела, которую ведёт анимация: родитель цепочки в скелете либо первые
  `smpStaticLinks` звеньев, как у пушистых хвостов. **Чего SMP не умеет:** столкновения
  у него идут от меша, а не от капсул на костях — `<per-vertex-shape>` называет ЧАСТЬ МЕША,
  и форму он строит по её вершинам сам. Поэтому севшие капсулы в SMP не переносятся; слой
  пишет только имена частей, на которых лежит кожа цепочки, с зазором из настроек.
  Подключить файл к части — `defaultBBPs.xml` (`<map shape="часть" file="…"/>`), руками.
- `presenters\cbpc.py` — строки трёх файлов CBPC, каждая под своей пометкой: `[ConfigMap]`
  для `CBPCMasterConfig*.txt` (кость = группа; своя кость у CBPC называется прямо, звенья
  одной цепочки в `<`…`>`, чтобы считались по порядку), `Группа.параметр значение`
  для `CBPConfig*.txt` и `[AffectedNodes]` с секциями `[Кость]` для `CBPCollisionConfig*.txt`,
  где капсула — `x,y,z,r & x,y,z,r | …`: концы через `&`, половины веса 0 и 100 через `|`
  (одинаковые: тело одно). Условие группы (`IsRaceName(...)`) дописывается самому,
  а секции столкновений вписываются в тот файл CBPC, что действует для этой расы.

Вывод — `physics … --out файл` либо на печать; `--json` даёт `{"engine", "chains"
(назначения всех цепочек и что из них записано), "text"}`.

**Проверка готового файла** (`physics --engine smp|cbpc --check файл`). Оба движка молчат
об ошибке в настройках: ни строки в журнале, просто ничего не качается. Слой каждого движка
умеет разобрать свой формат обратно (`smp.check`, `cbpc.check`) и сверить с тем, что есть:
кости `<bone>`, `[AffectedNodes]`, `[ColliderNodes]`, заголовки `[Кость]` и строки
`[ConfigMap]` — со скелетом, `<per-vertex-shape>`/`<per-triangle-shape>` — с частями меша,
шарниры — с объявленными костями, строки сфер и капсул — с их формой. Находка — строка
«род, имя, где, в чём дело», код выхода 3; чистый файл — код 0. Окупается первой же
опечаткой: `EarL Bone02` → `EarL Bone03` ловится за секунду, в игре это выглядело бы
как «уши не качаются» без объяснений.

## Журнал: уровни и приёмники

Журнал (`morphbench\journal.py`) отвечает на три **разных** вопроса, и смешивать их нельзя.
**Что писать** решает уровень записи (`debug`, `info`, `warn`, `error`) против порога приёмника.
**Куда** — набор приёмников: труба к тому, кто сервер запустил (окно запуска или консоль),
файл рядом с настройками, список в памяти для проверок. **Что при отказе** — выбывает один
приёмник, а не журнал: остальные получают и запись, и одну строку о выбывшем, и запись
не бросает наружу никогда.

Разделение это не украшение. Сервер писал строку прямо в трубу к окну; окно снимали, труба
закрывалась, запись падала — а падала она внутри отправки ответа, до заголовков, и клиент
получал обрыв связи без единого слова, хотя работа делалась. Отказ журнала уносил с собой
каждый обслуживаемый запрос. Глушить журнал в ответ на это нельзя: это меняет потерю связи
на потерю сведений.

Пороги у приёмников разные намеренно: опрос состояния (`/api/environment`, `/api/root` без
параметров) пишется уровнем `debug` и в окне не виден, а в файле остаётся — там он и нужен,
когда разбираются, что происходило. Передача корня — событие, а не опрос, и идёт уровнем
`info`. Настройки: `logLevel`, `logFile` (пусто — файл не вести), `logFileLevel`.

## Язык: ключи в коде, тексты в файлах

Исходник пишется по-английски, а **выводимых строк в коде нет вовсе**: вместо них стоят
ключи (`t("serve.portTaken", port=8767)`), а тексты лежат в `locale\`. Ключ - короткая
латинская метка, а не английская фраза: фразу правят при вычитке, и если она же служит
ключом, все переводы разом отвязываются от кода. Подстановка по имени, а не по месту:
в другом языке порядок слов другой.

**Язык - это папка, а не файл.** `locale\en\` и `locale\ru\`, а внутри - произвольное
число файлов по разделам: `cli.json`, `page.json`, `journal.json`, `serve.json`. При чтении
они сливаются в один словарь. Это не косметика: **новый раздел приходит новым файлом**,
и ни один существующий при этом не переписывается, поэтому две правки в разные разделы
не сталкиваются. Один ключ, объявленный в двух файлах одного языка, - ошибка раскладки:
берётся первый, а о столкновении сообщается, а не молчится.

Непереведённый ключ работу не ломает: берётся английский, а нет и его - показывается сама
метка, видимая и находимая поиском. Язык задаётся настройкой `language` (`auto` - язык
системы), а переменная окружения `MORPHBENCH_LANG` перевешивает её: этим пользуются
проверки, которые сверяются с текстами дословно и не должны зависеть от машины.

Страница в браузере словаря не видит - она по другую сторону провода. Поэтому весь её
раздел едет в полезной нагрузке одним объектом (`Catalogue.section("page.")`), уже на языке
запуска, а в скрипте стоит `T.secCapsules` и `say(T.errNoSlider, { name })` - та же
подстановка по имени.

Добавить язык - скопировать папку `locale\en\`, перевести правые части и назвать папку
кодом языка. Трогать код не нужно и нечем.

## Страница-смотрелка

`mb.py web` собирает один HTML-файл без единого обращения наружу: тело вращается мышью,
у каждого морфа свой ползунок, тело меняется живьём, вершины красятся по костям, по величине
сдвига выбранного морфа и по растяжению рёбер. Смещения морфов вложены в страницу двухбайтными
числами, как в самом формате TRIP. Каждое действие на странице — зеркало метода фасада, включая
орбиту мышью (`look`), панораму (`pan`) и размер холста (`resize`): внизу показывается состояние
показа тем же JSON, что даёт `view_state()`, и эквивалентная команда `mb.py render`, которой
этот же кадр получается без окна. Со скелетом (`--skeleton`) на панели появляется раздел
«Капсулы» с двумя галочками — обе зовут `show_colliders`, — и капсулы ложатся поверх тела так
же, как в PNG: полупрозрачно, со своей глубиной, не заслоняя кожу; в команду внизу при этом
попадают `--skeleton`, `--colliders` и `--bumper`.

## Настройки

Файл `morphbench.json` рядом с программой создаётся при первом запуске из встроенных умолчаний
и у каждой машины свой; ключи, которых в старом файле нет, дописываются в него сами. Там: путь
к PyNifly (пусто — искать в каталоге аддонов Blender), размер картинки, фон, ракурсы, свет,
имя базовой части `baseShape`, пороги разборов (`strainThreshold`, `boneShareMin`,
`leftBehindMin`, `boneMinVertices`, `frtriEpsilon`), точность бюджета амплитуд
`budgetResolution`, `contactRadius` и `minContact` для
смежности, `focusPadding` для наведения, `frameFill` для кадра, свет (`lightFollowCamera`,
`lightCameraDirection`, `lightDirection`, `ambient`, `diffuse`, `fill`, `shading`), обзор
(`catalogRoot`, `catalogSubdirs`), сервер (`serveHost`, `servePort`), журнал
(`logLevel`, `logFile`, `logFileLevel`), шары охвата
(`boundsMargin`, `boundsTolerance`), скелет и капсулы
(`skeletonFile`, `colliderSegments`, `colliderMinWeight`, `colliderFitPercentile`,
`colliderColour`, `colliderOpacity`), качающаяся физика (`chainEngines` — кому отдана
цепочка; числа тел, шарниров и форм `smp*`; числа группы и столкновений `cbpc*`),
`sliderRange`, `sliderStep`, `orbitSensitivity` и `wheelZoomRate` для страницы.

## Откуда берётся разбор форматов

Своих разборщиков NIF и TRI здесь нет намеренно. Меш читается библиотекой **nifly** через
её же обвязку из аддона **PyNifly**, файлы морфов — модулями `tri\trifile.py` и `tri\tripfile.py`
оттуда же. Это те самые модули, которыми морфы и пишутся, поэтому второго прочтения формата,
способного разойтись с первым, не появляется.

## Проверки

`python tests\run.py` прогоняет всё; каждый `tests\test_*.py` запускается и сам по себе. Фигуры
для проверок собираются в памяти и подключаются к фасаду через `MorphBench.attach`, поэтому
проверки не зависят ни от сборки, ни от путей. Там, где нужен PyNifly (настоящий файл TRIP или
NIF), проверка пропускается с причиной, если аддона на машине нет.

## Лицензия и чужое внутри

Верстак под **GNU GPL версии 3** — полный текст в `LICENSE`. Выбор не свободный: морфы читаются
и пишутся модулями PyNifly, а они несут блок GPL-3, и программа, включающая их, при раздаче
подчиняется той же лицензии. Условия эти нам и подходят: пользоваться, менять и встраивать можно
без спроса, передавать дальше — с исходниками, на тех же условиях и с сохранением авторских
отметок.

**Выпуск самодостаточен.** Внутри архива лежит всё: сам верстак, окно `morphbench.exe`,
встраиваемый Python, `numpy`, `pillow` и папка аддона **PyNifly**. Скачивать пользователю
нечего и ставить нечего - распаковал и запустил. Сам Blender не нужен и внутрь не идёт:
к `bpy` верстак не обращается, ему нужна только папка аддона.

Что именно кладётся внутрь, сказано в `dependencies.json`, и решает там **лицензия**,
а не удобство: PyNifly под GPL-3, как и мы, поэтому его можно и нужно класть; `numpy`
под BSD-3, `pillow` под MIT-CMU, Python под PSF. По тому же файлу собирается
`THIRD-PARTY.md` - перечень чужого с лицензиями и адресами исходников, который GPL
обязывает везти вместе с двоичным.

Собирает архив `release.py`, и **сам он в архив не попадает**: он принадлежит репозиторию,
а не выпуску. Он же единственное место, где перечислено содержимое, - перечислением,
а не исключением, поэтому соседние модули рабочей копии в архив попасть не могут.

    python release.py --version 0.9.0        собрать и запаковать
    python release.py --list                 что войдёт, ничего не делая
    python release.py --stage-only           разложить папку и не паковать

Отдельно к референсу: `dev\ref-bodyslide\` — исходники BodySlide, они читаются, но не копируются.

## Референс

В `dev\ref-bodyslide\` развёрнут исходный код **BodySlide and Outfit Studio**
(github.com/ousnius/BodySlide-and-Outfit-Studio, GPLv3) — эталонная реализация всего этого
хозяйства. Полезнее всего там `src\components\`: `DiffData` — хранение смещений морфа,
`Automorph` — перенос ползунка с эталонного тела на другой меш по близости вершин (тот же
приём, что у нашей смежности оболочек), `SliderData` и `SliderSet` — описание наборов
ползунков. Это **референс, а не заимствование**: код читается, повторяется своими средствами,
но не копируется — лицензии у нас разные.

# Командная строка

BodySlide строит тело; morphbench его проверяет. Он открывает `.nif` и лежащий рядом
`.tri`, сам применяет ползунки и отвечает числами: какие ползунки не двигают ничего, где
морф рвёт поверхность, накрывает ли шар охвата тело на полной амплитуде, где капсулы
столкновений перестают доставать до кожи и что должно быть написано в настройках SMP или
CBPC для качающихся костей. Ни игры, ни сохранения, ни порядка загрузки — секунды,
из папки.

`mb.py` — это всё оно целиком. Две вещи верны для каждой команды здесь:

* **Ко всякой команде подходит `--json`.** Таблицы — чтобы читать; `--json` — тот же
  ответ данными, поэтому проверка может жить в скрипте, а результат — сравниваться между
  двумя сборками. Ключ работает и до имени команды, и после: `mb.py --json shapes
  body.nif` и `mb.py shapes body.nif --json` — один и тот же вызов.
* **Страница в браузере не делает ничего, чего не может командная строка.** Страница —
  такой же клиент того же фасада (`morphbench/api.py`); её скрипт намеренно повторяет этот
  класс метод в метод, и каждый орган управления зовёт метод под собственным именем
  фасада. Отсюда и воспроизводимость сеанса: панель печатает ту строку `mb.py render`,
  которая даёт ровно то, что сейчас на экране, и её можно вставить в скрипт.
  См. [page.ru.md](page.ru.md).

Впервые здесь? Тогда сначала [quickstart.ru.md](quickstart.ru.md) — он проводит через
первый час. Этот файл — справочник: каждая команда, каждый ключ, что приходит в ответ.

## Как устроен вызов

```
python mb.py <команда> <меш.nif> [ключи]
```

Файл морфов подбирается рядом с мешем сам — то же имя либо имя без суффикса веса
`_0`/`_1`. Скелет подбирается так же: `skeleton.nif` в той же папке (имя файла задаёт
настройка `skeletonFile`). И тот и другой можно назвать явно, если они лежат в другом
месте.

| Ключ | Что принимает | Что делает |
|---|---|---|
| `nif` | путь | меш, который открыть. Обязателен везде, кроме `colliders`, `fit`, `render`, `sheet` и `web` |
| `--tri` | путь | файл морфов, когда он лежит не рядом с мешем или назван иначе |
| `--skeleton` | путь | скелет, из которого читаются капсулы столкновений |
| `--json` | — | тот же ответ данными вместо таблиц |

`fit`, `render`, `sheet` и `web` умеют брать меш из обзора вместо пути:

```
python mb.py render --entry 42 --root "D:\...\Data" --out frame.png
```

`--entry` — номер, который печатает `catalog`, либо путь от корня как имя; `--root` —
папка, которой эта нумерация принадлежит (под MO2 по умолчанию это `Data` игры, где видны
сразу все моды сборки).

Трём командам меш не нужен вовсе: `env`, `catalog` и `serve`. Команде `colliders` хватает
одного скелета — капсулы можно посмотреть и без тела перед ними.

**Коды выхода.** `0` — команда ответила. `2` — отказ: меша нет, ключ написан неверно,
скелет отсутствует. Отказ — это одна строка в stderr (`команда: в чём дело`), а не
трассировка стека, потому что её должен уметь прочитать скрипт. `3` — только
у `physics --check` и только когда нашлись замечания: чистый файл даёт `0`.

**Язык.** Сообщения, справка и заголовки колонок берутся из `locale/<язык>/`, а сам язык
выбирает настройка `language` (`auto` следует за системой). Переменная окружения
`MORPHBENCH_LANG` перекрывает настройку — это дверь для прогона, который не должен
зависеть от машины, где он идёт. См. [localisation.ru.md](localisation.ru.md).

**Пары чисел, начинающиеся с минуса, пишутся через знак равенства:** `--pan=-5,3`,
`--look=-10,5`. Без него argparse принимает значение за очередной ключ.

## Что лежит в файле

### `summary`

Что открыто: меш, файл морфов и его формат, счётчики, скелет и габарит всего тела.

```
python mb.py summary body.nif
```

Своих ключей нет. `--json` возвращает один объект: `nif`, `tri`, `triKind`, `shapes`,
`vertices`, `bones`, `morphs`, `skeleton`, `colliders`, `bounds` (`min`/`max`).

### `shapes`

Части меша, по строке на каждую: вершины, треугольники, кости, сколько ползунков трогает
эту часть, и её габарит.

```
python mb.py shapes body.nif
```

Своих ключей нет. `--json` даёт список `{name, vertices, triangles, bones, morphs,
bounds}`.

### `bones`

Какая кость держит сколько вершин, тяжёлые первыми. Полезно перед любым делом, связанным
с физикой: кость, держащая восемь вершин, не раскачает ничего.

```
python mb.py bones body.nif --find Thigh
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--shape` | имя части | считать только внутри этой части; иначе по всем |
| `--find` | подстроку | только кости, чьё имя её содержит, регистр не важен |

`--json` даёт список `{bone, vertices}`.

### `morphs`

Что каждый ползунок на самом деле делает: сколько вершин двигает, насколько сильно
в худшей точке и в среднем, и в какой коробке эти сдвинутые вершины лежат.

```
python mb.py morphs body.nif --morph CLAWPawSize
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--morph` | имя ползунка | один ползунок; иначе все |
| `--shape` | имя части | одна часть; иначе все |

`--json` даёт список `{shape, morph, vertices, maxShift, meanShift, bounds}`.

### `empty`

Ползунки, которые в файле есть и не двигают ничего.

```
python mb.py empty body.nif
```

Это одна из двух молчащих поломок. Ползунок, который ничего не двигает, выглядит
совершенно здоровым в любом инструменте, который только перечисляет имена; в игре это
орган управления, который не работает. `--json` даёт те же строки, что и `morphs`, —
`{shape, morph, vertices, maxShift, meanShift, bounds}`, где у каждой `vertices` равно 0,
сдвиги равны 0, а `bounds` — `null`; пустой список, когда всё в порядке. В таблице
показаны только те две колонки, в которых что-то есть.

### `missing`

Вторая молчащая поломка: ползунки, которые обещал рецепт, а в файле их нет.

```
python mb.py missing body.nif CLAWNeck CLAWEars CLAWPawSize
```

Имена идут позиционно, и их может быть сколько угодно. `--json` даёт простой список
имён, которых в файле нет, — пустой, когда есть все.

## Что морфы делают с поверхностью

### `strain`

Растяжение рёбер: насколько меняется длина ребра под морфом. Ноль означает, что часть
сдвинулась целиком и сохранила форму. Большое значение означает, что один конец ребра
уехал, а другой остался, — поверхность растянута или разорвана. Худшие рёбра дают
коробку, поэтому ответ говорит ещё и где именно, а не только насколько плохо.

Под одной этой командой живут три разных вопроса.

**Один ползунок или все по очереди:**

```
python mb.py strain body.nif --morph CLAWPawSize --amount 1.0
```

**Набор ползунков разом** — смещения складываются, как они складываются в игре:

```
python mb.py strain body.nif --slider CLAWTorsoBreastSize=1 --slider CLAWTorsoChestSize=1
```

**Все пары ползунков** — чтобы найти сочетания, которые рвут сильнее любой своей половины:

```
python mb.py strain body.nif --pairs --by gain --top 20
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--morph` | имя ползунка | один ползунок; иначе все |
| `--amount` | число | величина, на которую выставлен ползунок; по умолчанию `1.0` |
| `--threshold` | число | растяжение, с которого ребро считается разорванным; по умолчанию `strainThreshold` (0.25) |
| `--slider` | `ИМЯ=ЧИСЛО` | значение в наборе; ключ повторяется для каждого ползунка. `--morph` и `--amount` в этом режиме не действуют |
| `--pairs` | — | перебрать все пары непустых ползунков на величине `--amount` |
| `--top` | число | сколько худших пар показать; по умолчанию `10`, `0` — все |
| `--by` | `max` или `gain` | чем упорядочены пары: растяжением вдвоём или прибавкой пары сверх худшего из двух поодиночке |

Зачем нужен `--by gain`: при сортировке по растяжению верх таблицы занимают все пары
с самым рвущим одиночкой, и прибавка у них нулевая — они не говорят ничего, чего не было
бы видно из прогона по одиночным ползункам. Прибавка — это то, что даёт именно
*сочетание*.

`--json`: одиночная форма и форма набора возвращают строки `{shape, edges, maxStrain,
p99Strain, overThreshold, threshold, worstBounds}`, причём в одиночной есть `morph` (имя),
а в наборе — `sliders` (объект «имя → значение»). `--pairs` возвращает `{a, b, amount,
maxStrain, overThreshold, shape, maxA, maxB, gain, threshold}`.

### `budget`

Для каждого ползунка — величина, на которой он впервые переходит порог растяжения.
Двоичный поиск в пределах `sliderRange` с точностью `budgetResolution`.

```
python mb.py budget body.nif --threshold 0.25
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--threshold` | число | порог растяжения; по умолчанию `strainThreshold` |

Это превращает «амплитуды нарочно завышены, потом сведём» в таблицу чисел. Рвущие идут
первыми, по возрастанию предела, — в этом порядке с ними и работать. `--json` даёт
`{morph, limit, maxAt, shape, threshold, high}`, а там, где диапазон ползунка уходит ниже
нуля, ещё и `limitLow`. `limit`, равный `null`, означает, что в пределах диапазона
ползунок нигде не рвёт, а `maxAt` говорит, насколько далеко он остался от порога.

### `layers`

Следуют ли внешние оболочки за кожей. Кожа двигается своим морфом, а шерсть поверх неё —
своей копией этого морфа; если у копии амплитуда меньше или копии нет вовсе, слои
расходятся и сквозь шерсть проступает тело.

```
python mb.py layers body.nif --morph CLAWBelly --adjacent
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--morph` | имя ползунка | **обязателен**: под каким морфом судить о слоях |
| `--base` | имя части | часть, за которой оболочки следуют; по умолчанию `baseShape` (`body`) |
| `--adjacent` | — | только оболочки, лежащие над реально сдвигаемой кожей, — те, что обязаны следовать |

`--base` — не украшение. Заплатка шва между двумя слоями шерсти не лежит на коже вообще,
и вопрос о ней относительно тела даёт нулевое касание и бессмысленный вердикт; спрашивать
надо относительно того слоя, который она сшивает (`--base fur_belly`).

`--json` даёт `{morph, base, baseMax, follower, followerMax, ratio, missing, contact,
adjacent, expectedMax}`. `ratio` — амплитуда оболочки против амплитуды кожи; `contact` —
доля вершин оболочки, лежащих над сдвинутой кожей; `adjacent` говорит, перешла ли эта доля
`minContact`; `expectedMax` — насколько сдвинулась кожа прямо под оболочкой, то есть
насколько должна была сдвинуться и она сама.

### `binding`

Каким костям принадлежат вершины, которые двигает морф, и какие кости он двигает лишь
наполовину. Второй список — это места, где поверхность растягивается: морф, который
двигает одну часть кости и бросает другую, тянет кожу, как перчатку на лапе.

```
python mb.py binding body.nif --morph CLAWPawSize --shape body
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--morph` | имя ползунка | **обязателен** |
| `--shape` | имя части | на какую часть смотреть; по умолчанию `baseShape` |

`--json` возвращает один объект с двумя списками: `touched` (`{bone, share}`)
и `leftBehind` (`{bone, leftBehind}`).

## Шары охвата

### `bounds`

У каждой части меша записан шар — центр и радиус, — по которому игра решает, попадает ли
часть в кадр. Шар считается при экспорте по телу **в покое**, и морфы его не расширяют.
Деталь, которую ползунок вытянул за пределы шара, пропадает, как только шар уходит
из кадра, — а сама деталь при этом ещё на экране. Именно это моргание команда и объясняет.

```
python mb.py bounds body.nif
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--shape` | имя части | одна часть; иначе все |
| `--margin` | число | запас сверх нужного радиуса, множителем; по умолчанию `boundsMargin` (1.01) |
| `--write` | путь | записать исправленные шары в **новый** файл меша |
| `--shrink` | — | при записи ещё и сжимать шары до нужного размера; без него шар только расширяется |

Запись поверх исходника отвергается: меш принадлежит чужому моду, а правки ездят
отдельным модом. Шар, который и так всё накрывает, остаётся как есть, а шар шире нужного
сохраняется: широкий шар иногда сделан нарочно — под шерсть с качающейся физикой, — и ядро
никак не может об этом знать. `--shrink` означает, что это осознанное решение.

```
python mb.py bounds body.nif --write "out\body.nif"
```

`--json` даёт на каждую часть `{shape, block, vertices, morphs, needed, file, reach,
excess, state, single, singleReach, overCap, ok}`. `reach` — насколько далеко геометрия
уходит от центра шара, записанного в файле, при худшем наборе ползунков; `excess` —
насколько это дальше радиуса, долей; `state` называет виноватый набор, а `single` — тот
единственный ползунок, который уводит дальше всех поодиночке. `overCap` считает вершины,
которых касается больше ползунков, чем `boundsCornerCap`: такие оцениваются, а не
перебираются точно, и пока он ноль — ответ точен. `--write` возвращает `{saved, shapes,
kept, rows}`.

Что означают эти числа и почему перебор точен — в [physics.ru.md](physics.ru.md).

## Капсулы столкновений

### `colliders`

Капсулы из скелета: где стоят, какого рода, и — с ключом `--clearance` — как они сидят
по коже при нынешних ползунках.

```
python mb.py colliders --skeleton skeleton.nif --find Thigh
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--find` | подстроку | только кости, чьё имя её содержит |
| `--clearance` | — | ещё и померить капсулы по коже; тогда нужен и меш |

Меш здесь необязателен — капсулы стоят сами по себе. `--clearance` — исключение, и оно
об этом говорит: он сравнивает их с кожей, значит, ему нужно тело.

```
python mb.py colliders body.nif --skeleton skeleton.nif --clearance
```

`--json` даёт `{bone, kind, physics, capsules}`, а с `--clearance` на каждой записи ещё
объект `clearance`: `{bone, points, worst, deepest, mean, outside}`. Внутри капсулы
расстояние отрицательное, поэтому большая доля `outside` вместе с большим `worst`
означают, что капсула не достаёт до кожи и рука пройдёт сквозь тело; сильно отрицательный
`deepest` означает, что капсула торчит из тела наружу.

### `fit`

Посадить капсулы по коже при нынешних значениях ползунков. Ради этого верстак вообще
берётся за коллайдеры: тело здесь уже деформировано, каждая вершина известна, поэтому
посадку можно вычислить точно, а не подбирать наугад в игре.

```
python mb.py fit body.nif --skeleton skeleton.nif --slider CLAWTorsoBreastSize=1
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--find` | подстроку | только кости, чьё имя её содержит |
| `--percentile` | число | доля точек, которая обязана попасть внутрь радиуса; по умолчанию `colliderFitPercentile` (90) |
| `--bundle` | число | посадить связку из N капсул вместо одной: облако кожи режется на куски |
| `--split` | `axis` или `kmeans` | как резать — ломтиками вдоль оси кости или сгустками по близости; по умолчанию `bundleSplit` |
| `--save` | путь | записать **новый** файл скелета с капсулами в их нынешнем виде |
| `--ppb` | — | ещё и напечатать строки настроек для Precision Physic Bodies |
| `--slider` | `ИМЯ=ЧИСЛО` | значение ползунка; ключ повторяем — это и есть поза, по которой сажают |
| `--only` | имена через запятую | какие части меша считать кожей |
| `--entry`, `--root` | | взять меш из обзора вместо пути |

Процентиль, а не самая дальняя точка, потому что одна торчащая вершина раздула бы капсулу
в одиночку. `--save` всегда пишет новый файл — по той же причине, по которой это делает
`bounds --write`. `--ppb` существует потому, что PPB перечитывает свой `PPB_tuning.txt`
примерно раз в секунду прямо во время игры, и строки можно пробовать вживую, ничего
не перезапуская; свои настройки PPB называет по слотам тела, и ни для хвоста, ни для
пальцев такого слота нет, поэтому эти кости пропускаются, а не получают выдуманное имя.

`--json` возвращает `{fitted: [...]}`, а рядом `saved` и `ppb`, если эти ключи были даны.
Строка посаженной кости — `{bone, points, fitted, was, wasCount, now, count, capsules}`;
кость, не давшая ни одной точки кожи, возвращается как `{bone, points, fitted: false}`.

## Качающаяся физика

Полный рассказ о том, что верстак здесь меряет, — цепочки, обрывы, числа, идущие в каждый
движок, — в [physics.ru.md](physics.ru.md). Этот раздел — про команды.

### `chains`

Нумерованные цепочки костей (`TailBone01`, `TailBone02`, …): сколько кожи висит на каждом
звене, где цепочка обрывается, годится ли она вообще для качания и какому движку отдана.

```
python mb.py chains body.nif --skeleton skeleton.nif
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--engine` | `smp` или `cbpc` | только цепочки, отданные этому движку |
| `--only` | имена через запятую | по каким частям меша считать кожу |
| `--assign` | `tail=smp,ear=cbpc` | кому отдана цепочка на этот запуск, поверх настройки `chainEngines` |

Скелет не обязателен: цепочки читаются по костям, к которым привязан меш. Со скелетом
известен ещё и родитель каждой цепочки — а он нужен файлу физики.

`--json` даёт `{chain, engine, parent, links, vertices, break, anchors, gaps, tail, tip,
fit}`; каждое звено — `{bone, number, vertices, parent, shapes}`.

### `physics`

Настройки одного качающего движка его собственным форматом: SMP — как XML, CBPC — как
строки трёх его файлов. Цепочки, отданные другому движку, не пишутся: SMP и CBPC — разные
движки, и одну кость обоим отдать нельзя. В шапке текста сказано, какая цепочка куда ушла
и какая не досталась никому.

```
python mb.py physics body.nif --skeleton skeleton.nif --engine smp --out tail.xml
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--engine` | `smp` или `cbpc` | **обязателен**: для какого движка писать |
| `--assign` | `tail=smp,ear=cbpc` | кому отдана цепочка на этот запуск, поверх настроек |
| `--out` | путь | записать текст в файл; без него текст печатается |
| `--check` | путь | проверить готовый файл вместо того, чтобы писать новый |
| `--percentile` | число | доля точек внутри радиуса капсулы; по умолчанию из настроек |
| `--slider` | `ИМЯ=ЧИСЛО` | значения ползунков, при которых меряются капсулы; ключ повторяем |
| `--only` | имена через запятую | какие части считать кожей |

Скелет обязателен: без него цепочку не на что вешать.

`--json` возвращает `{engine, chains, text}`, а с ключом `--out` ещё и `saved`. Каждая
запись в `chains` — `{chain, engine, fit, break, vertices, written}`, где `written`
говорит, попала ли цепочка в текст.

**Проверка файла, который уже есть:**

```
python mb.py physics body.nif --skeleton skeleton.nif --engine smp --check tail.xml
```

SMP пропускает сломанный файл молча — ни строки в журнале, просто ничего не качается.
Эта проверка ловит то, во что обходится первая же опечатка: кость, которой в скелете нет;
шарнир на кость, которую никто не объявил; часть меша, которой не существует;
столкновение между тем, чего никто не называл; XML, который не разбирается. Для CBPC она
читает за один проход разделы всех трёх файлов: узлы, заголовки `[Bone]` с их шарами
и капсулами, строки `Bone=Group`.

Смысл этого режима — в коде выхода: **3**, когда есть замечания, **0**, когда файл
ссылается только на существующее. Это и делает его пригодным для заслона в сборочном
скрипте.

`--json` возвращает `{file, engine, problems, ok}`, где каждое замечание — `{kind, name,
where, problem}`.

## Посмотреть глазами

### `focus`

Наведение камеры, числами. С одним из трёх ключей команда печатает, куда камера будет
смотреть и насколько широко; без них — перечисляет всё, на что её можно навести.

```
python mb.py focus body.nif --bone "L Finger"
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--bone` | имя или подстроку | кость или все подходящие кости — `L Finger` это вся левая лапа |
| `--morph` | имя ползунка | область, которую двигает этот морф |
| `--shape` | имя части | одна часть меша |

`--json` даёт `{name, centre, radius}` для цели либо `{shapes, bones, morphs}` — три
списка того же самого, — когда ни один ключ не задан.

### `render`, `sheet`, `web`

Три команды, один набор ключей показа. `render` пишет один PNG, `sheet` пишет несколько
ракурсов в папку, `web` пишет страницу-смотрелку одним самодостаточным HTML-файлом,
который открывается с диска без всякого сервера за спиной.

```
python mb.py render body.nif --out frame.png --view quarter --colour strain --morph CLAWPawSize
```

```
python mb.py sheet body.nif --out shots --views front,side,below
```

```
python mb.py web body.nif --out page.html
```

`--out` обязателен у всех трёх: путь к файлу у `render` и `web`, папка у `sheet`.

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--view` | `front`, `side`, `back`, `top`, `below`, `quarter` | готовый ракурс из настройки `views` |
| `--look` | `поворот,подъём` в градусах | произвольный ракурс; с минусом писать `--look=-10,5` |
| `--colour` (`--color`) | `shade`, `bone`, `morph`, `strain` | чем красится поверхность; по умолчанию `shade` |
| `--morph` | имя ползунка | о каком морфе речь при `--colour morph` и `--colour strain` |
| `--slider` | `ИМЯ=ЧИСЛО` | значение ползунка; ключ повторяем |
| `--only` | имена через запятую | какие части показывать |
| `--zoom` | число | масштаб |
| `--zoom-at` | `масштаб,x,y` | масштаб к точке: точка в долях половины меньшей стороны кадра от центра, вправо и вверх |
| `--pan` | `вправо,вверх` в единицах модели | сдвиг кадра; с минусом писать `--pan=-5,3` |
| `--size` | `ШИРИНАxВЫСОТА` | размер кадра, например `900x900` |
| `--light` | `camera` или `world` | свет за камерой, едущий вместе с кадром, либо закреплённый в мире |
| `--light-dir` | `x,y,z` | направление на источник — в осях камеры (вправо, вверх, к зрителю) при `--light camera`, иначе в мировых |
| `--light-power` | `ambient[,diffuse[,fill]]` | три силы; `fill` — встречная подсветка, не дающая теням ослепнуть |
| `--focus-bone` | имя или подстроку | навести на кость |
| `--focus-morph` | имя ползунка | навести на то, что двигает морф |
| `--focus-shape` | имя части | навести на одну часть |
| `--colliders` | — | нарисовать поверх тела капсулы столкновений; нужен скелет |
| `--bumper` | — | и цилиндр перемещения, который вчетверо больше тела |
| `--entry`, `--root` | | взять меш из обзора вместо пути |

У `sheet` есть ещё два своих: `--views` (список ракурсов через запятую; по умолчанию все)
и `--prefix` (начало каждого имени файла; по умолчанию `view`, что даёт
`view-front.png`).

Ключи применяются в жёстком порядке, а не в том, в каком их набрали, и две пары
перекрываются: `--look` применяется после `--view`, а `--zoom-at` — после `--zoom`,
так что в каждой паре побеждает второй. Ключи наведения применяются до ракурса, поэтому
наведение и поворот складываются, а не гасят друг друга.

`--json` возвращает `{saved, view, sliders}` у `render` и `web` и `{saved: [пути]}`
у `sheet`. Объект `view` — это всё состояние показа: ракурс, масштаб, панорама, раскраска,
видимые части, свет, наведение, — и это тот же объект, который страница показывает внизу
своей панели. В этом и состоит круг: нажать что-нибудь на странице, скопировать
напечатанную строку, запустить её здесь.

Страница, которую пишет `web`, собрана из настоящих файлов — `web/page.html`,
`web/style.css` и скриптов из `web/js/`, — свёрнутых в один. Сервер раздаёт те же файлы
по отдельности, чтобы правка была видна по перезагрузке; `web` встраивает их внутрь, чтобы
результат можно было отправить письмом или положить рядом с отчётом. Обе формы собирает
`presenters/assets.py`, а порядок загрузки скриптов объявлен один раз,
в `PageAssets.SCRIPTS`. Что делает сама страница — в [page.ru.md](page.ru.md).

## Где мы запущены и что вокруг

### `env`

Под Mod Organizer 2 ли этот процесс, какие игры видны и какой корень обзора остаётся
по умолчанию.

```
python mb.py env
```

Быть под MO2 важно: там `Data` игры — это вся сборка, все её моды одним слоем, и только
там можно прочитать тело таким, каким его собирает игра. Вне MO2 папку приходится
называть.

`--json` даёт `{insideMo2, dataRoot, games, catalogRoot, candidates}`.

### `catalog`

Меши под папкой, пронумерованные, с подобранным к каждому файлом морфов. Обход не
открывает файлы — он подбирает по имени, — поэтому он быстр даже по всей сборке.

```
python mb.py catalog --find femalebody
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `root` | путь (позиционный) | папка, которую обойти; по умолчанию `Data` игры под MO2 либо `catalogRoot` |
| `--all` | — | перечислить и меши без файла морфов |
| `--find` | подстроку | только пути, её содержащие |

Номера, которые печатает эта команда, и принимает `--entry`. `--json` даёт `{index, name,
nif, tri, kind, folder, file}`, где `name` — путь от корня, а `folder` и `file` — тот же
путь, разделённый надвое.

### `serve`

Страница со списком мешей на локальном порту, чтобы тело можно было выбрать, ничего
не перезапуская.

```
python mb.py serve
```

| Ключ | Что принимает | Что делает |
|---|---|---|
| `--root` | путь | корень обзора; умолчание то же, что у `catalog` |
| `--nif` | путь | меш, открываемый сразу |
| `--tri` | путь | его файл морфов |
| `--host` | адрес | по умолчанию `serveHost` (127.0.0.1) |
| `--port` | число | по умолчанию `servePort` (8767) |
| `--all` | — | перечислить и меши без файла морфов |
| `--no-browser` | — | не открывать браузер |
| `--parent` | номер процесса | сервер уходит вместе с этим процессом |
| `--status` | — | спросить, поднят ли сервер на этом адресе |
| `--stop` | — | остановить поднятый сервер |

**Команда идемпотентна, и это сделано намеренно.** Без ключей она поднимает сервер. Если
на этом адресе сервер уже поднят, второй не поднимается: она отдаёт поднятому корень
обзора — под MO2 ту `Data`, которую этот процесс видит сквозь подмену, — и открывает
страницу. Поэтому одна и та же команда годится независимо от того, запущено что-нибудь
или нет, и правило живёт в одном месте, а не в каждом вызывающем. Сервер, который поднят,
но был запущен **вне** MO2, мешей сборки не видит, и корень от MO2 ему не передаётся —
отказ приходит словами, а не тишиной.

`--parent` существует потому, что окно, убитое жёстко — «Снять задачу», аварийное
завершение, выход из системы, — остановить свой сервер не успевает. Без сторожа процесс
остался бы висеть невидимым: порт занят, его картина сборки уже устарела, а следующий
запуск молча подключился бы к нему. С номером процесса сервер ждёт этот процесс по-честному
и освобождает порт.

```
python mb.py serve --status
```

```
python mb.py serve --stop
```

`--status` говорит ещё и о том, что видит **этот** процесс, — и именно это полезно, когда
две картины расходятся: сервер, поднятый вне MO2, и команда, запущенная изнутри неё,
разойдутся в корне, а состояние делает расхождение видимым вместо того, чтобы оставить
гадать, почему список пуст.

`--json` при подъёме даёт `{started, url, root, insideMo2}`; при передаче поднятому
`started` равно `false`, а `handed` несёт то, что поднятый сервер принял. `--status` даёт
`{state, url, insideMo2, root, meshes}` — а когда сервер наш, ещё и `dataRoot`, который
видит он сам, — плюс `hereInsideMo2`, `hereDataRoot`
и `hereCandidates` — про этот процесс; `state` — одно из `free`, `ours`, `busy` (порт
занят чужой программой) или `slow` (на соединение что-то отвечает, а на запрос нет,
и понять, кто это, нельзя). `--stop` даёт `{stopping, url}`.

Окно `morphbench.exe`, стоящее рядом со всем этим, делает то же самое кнопками и ничего
не считает само: каждая кнопка — один из перечисленных вызовов, а адрес и окружение оно
узнаёт из `serve --status --json`, а не из собственных умолчаний. Запуск его из MO2 — это
и есть способ, которым сервер начинает видеть сборку. Настройка MO2 —
в [quickstart.ru.md](quickstart.ru.md), сборка самого окна — в [building.ru.md](building.ru.md).

## Настройки за умолчаниями

Везде, где выше сказано «из настроек», имеется в виду `morphbench.json` рядом с кодом,
который создаётся при первом запуске из встроенных умолчаний. Ничего настраиваемого
не лежит в коде числом. Ключи, на которые опирается командная строка, — это
`strainThreshold`, `budgetResolution`, `sliderRange`, `boundsMargin`, `boundsTolerance`,
`boundsCornerCap`, `baseShape`, `contactRadius`, `minContact`, `skeletonFile`,
`colliderFitPercentile`, `bundleSplit`, `chainEngines`, `catalogRoot`, `serveHost`,
`servePort`, `views` и `language`. Ключ всегда старше настройки и только на этот запуск:
`--assign` и `--percentile` в файл ничего не пишут.

Полный список, включая все числа SMP и CBPC, — в [physics.ru.md](physics.ru.md)
и в комментариях `morphbench/config.py`, которые и есть источник истины.

# morphbench: первый час

BodySlide собирает тело, morphbench проверяет, что получилось. Он открывает собранное — `.nif`,
лежащий рядом `.tri` с морфами, скелет — и отвечает, сходятся ли ползунки, шары охвата, капсулы
столкновений и настройки качающейся физики. Без игры, за секунды, не загружая сохранение
и не запуская Blender.

Эта страница — про первый час: распаковать, открыть меш, прочитать ответ и два способа запуска —
из командной строки и из Mod Organizer 2, чтобы были видны меши всей сборки. Все команды и все
ключи — в [cli.ru.md](cli.ru.md); что числа значат физически — в [physics.ru.md](physics.ru.md);
весь верстак целиком — в [../README.ru.md](../README.ru.md).

## Что нужно

Верстак бывает в руках двумя способами, и от машины они требуют разного.

| | Из архива выпуска | Из рабочей копии |
|---|---|---|
| Python 3.12 | внутри, в `python\` | установлен, в `PATH` |
| `numpy` | внутри, в `vendor\` | `pip install numpy` |
| `pillow` | внутри, в `vendor\` | `pip install pillow` |
| аддон PyNifly | внутри, в `vendor\io_scene_nifly` | в каталоге аддонов Blender |
| `morphbench.exe` (окно, которое запускает MO2) | внутри, рядом с `mb.py` | собирается `launcher\build.cmd` |

Выпуск задуман самодостаточным: его распаковывают куда угодно и держат папку целиком — больше
скачивать нечего. `pillow` — единственная необязательная часть: без него работает всё, кроме
записи кадров PNG (`render`, `sheet`).

**PyNifly не необязателен, и он не наш.** Это единственный здесь читатель NIF и TRI; своих
разборщиков этих форматов у верстака нет и быть не должно — второе чтение формата это то, что
может тихо разойтись с первым. Из рабочей копии он ищется в
`%APPDATA%\Blender Foundation\Blender\<версия>\scripts\addons\io_scene_nifly`; лежит в другом
месте — папка называется ключом `pynifly` в `morphbench.json`. Когда его нет нигде, ответ прямой:
*не найден аддон PyNifly; укажите его папку ключом pynifly в morphbench.json*. **Сам Blender
не нужен**: к `bpy` верстак не обращается, читается только папка аддона — она просто обычно лежит
среди аддонов Blender.

Одну шероховатость стоит знать до того, как она укусит: `morphbench.exe` ищет python
по переменной `MORPHBENCH_PYTHON`, затем по ключу `python` в `morphbench.json`, затем в `PATH`,
реестре и через `py.exe`. Папку `python\`, которая лежит рядом с ним внутри архива выпуска, он
пока **не** замечает. На машине, где Python не установлен, путь придётся указать руками: вписать
в `MORPHBENCH_PYTHON` полный путь до `python\python.exe` в распакованной папке либо тот же путь
в `morphbench.json` под ключом `"python"`. Ключи, которых программа не знает, при перезаписи файла
сохраняются, так что строка не пропадёт.

## Как открыть меш

Все команды идут из папки модуля, той, где лежит `mb.py`:

```
python mb.py summary "meshes\actors\character\character assets\femalebody_1.nif"
```

Из выпуска, где python лежит внутри и может не быть в `PATH`, тот же вызов пишется
`python\python.exe mb.py ...`.

В ответ приходят четыре строки, и в первый раз их стоит прочитать медленно:

| строка | о чём говорит |
|---|---|
| `меш:` | какой файл открыт |
| `морфы:` | найденный рядом файл морфов и его формат — `TRIP` или `FRTRI` |
| `частей / вершин / костей / ползунков` | насколько велика эта штука и сколько в ней ползунков |
| `охват:` | коробка, которую геометрия занимает в покое, в единицах модели |

Строка `морфы:` со словом `нет` — уже ответ: тело собрано без морфов, и всякой проверке ползунков ниже
просто не над чем работать.

Два файла подбираются без указания. Файл морфов — тот, что лежит рядом с мешем под тем же именем
без суффикса веса (`femalebody_1.nif` → `femalebody.tri`); другой называется ключом `--tri`.
Скелет `skeleton.nif` в той же папке открывается вместе с мешем; другой называется ключом
`--skeleton`. Важны оба, потому что капсулы лежат в скелете, а не в теле.

Ко всякой команде подходит `--json`: тот же ответ машинно. Это те же данные, которыми живут
страница и окно, — второй реализации за ними нет, — поэтому всё, что увидено глазами, кладётся
в скрипт без повторного вывода чисел.

Сообщения выходят на языке системы. `MORPHBENCH_LANG=en` (или `ru`) перебивает это на один запуск,
настройка `language` — насовсем. Язык здесь — папка маленьких файлов JSON, а не один файл, поэтому
добавление языка не трогает ни одной существующей строки; см. [localisation.ru.md](localisation.ru.md).

## Вопросы первого часа

| что надо узнать | команда |
|---|---|
| что вообще лежит в этом файле | `summary`, `shapes`, `bones`, `morphs` |
| мёртв ли ползунок или его нет вовсе | `empty`, `missing` |
| не растягивает и не рвёт ли морф поверхность | `strain` |
| следуют ли оболочки за кожей под морфом | `layers` |
| не пропадает ли деталь под некоторыми ракурсами | `bounds` |
| где стоят капсулы столкновений и насколько промахиваются | `colliders --clearance` |
| что может качаться, на каком движке и здоров ли файл настроек | `chains`, `physics` |
| как это вообще выглядит | `render`, `web`, `serve` |

Все ключи, умолчания и вид каждого ответа `--json` — в [cli.ru.md](cli.ru.md).

## Кадр и страница

```
python mb.py render body_1.nif --view side --colour strain --morph CLAWBelly --out frame.png
```

```
python mb.py web body_1.nif --out page.html
```

`render` пишет один PNG. `web` пишет **один** HTML-файл без единого обращения наружу:
открывается с диска, тело вращается левой кнопкой, колесо — масштаб к точке под курсором, правая
кнопка — панорама, двойной щелчок — сброс. У каждого ползунка меша свой движок, и тело меняется
на глазах. Внизу панели страница показывает состояние показа тем же JSON, что даёт `--json`,
и равносильную команду `mb.py render` — так что найденное руками мышью повторяется в скрипте
без угадывания чисел.

Страница теперь собрана из обычных файлов — `web/page.html`, `web/style.css` и
`web/js/{core,shapes,view,bench,render,panel,app,boot}.js`, — и единственное, что знает, как они
становятся одной страницей, — `presenters/assets.py`. Складывает он их двумя способами: сервер
отдаёт файлы по одному под `/web/...`, и тогда перезагрузка браузера показывает правленый скрипт
с настоящими именами файлов и настоящими номерами строк, а `save()` сворачивает всё в один
самодостаточный файл для `file://`. Порядок загрузки объявлен один раз, в `PageAssets.SCRIPTS`,
и больше нигде. Что делает каждая панель и что значат цвета — в [page.ru.md](page.ru.md).

## Запуск из Mod Organizer 2

Под MO2 моды слиты в один `Data` игры подменой usvfs, и **этот слитый Data видит только процесс,
запущенный самой MO2**. Меши сборки лежат там и больше нигде, поэтому верстак приходится
запускать из MO2 — а MO2 запускает исполняемые файлы, не скрипты. В этом и весь смысл
`morphbench.exe`: запущенный из MO2, он поднимает `python mb.py serve` своим потомком, и этот
потомок видит Data со всеми модами.

1. Из рабочей копии окно собирается один раз. Ставить нечего: `csc.exe` из .NET Framework 4 есть
   на любой Windows, а результат ложится рядом с `mb.py`. В архиве выпуска exe уже лежит — этот
   шаг пропускается. Подробности и значок — в [building.ru.md](building.ru.md).

```
launcher\build.cmd
```

2. В MO2 открыть список исполняемых файлов (кнопка с шестерёнкой), добавить запись и указать
   в **Binary** `<путь к morphbench>\morphbench.exe`. В **Arguments** можно вписать `--start`,
   чтобы сервер поднимался и страница открывалась одной кнопкой. «Start in» можно оставить пустым.

3. Запустить эту запись из MO2. Строка состояния окна должна сказать, что оно под MO2, и показать
   `Data` игры как корень обзора. Сервер, поднятый оттуда, видит меши всех модов, и выйти
   за пределы `Data` страница не даст. Сервер, поднятый **вне** MO2, окно опознаёт и предлагает
   остановить: мешей сборки он не видит, а молча им пользоваться — худший из возможных исходов.

**Окно - удобство, а не условие.** MO2 запускает исполняемые файлы, а не сценарии, и только
поэтому окно вообще появилось, - но `python.exe` тоже исполняемый файл. Запись, у которой
в **Binary** стоит `<путь к morphbench>\python\python.exe`, а в **Arguments** - `mb.py serve`,
делает ту же работу: usvfs MO2 подсаживает в неё точно так же, и сервер видит ту же собранную
`Data`. Для такого варианта в **Start in** указывается папка верстака. Тот, кто не хочет
запускать скачанный из интернета неподписанный бинарник, работает так и теряет только кнопки.

Без MO2 то же самое проверяется из командной строки: ответ будет `под MO2: нет`, а следом
перечень игр, найденных в реестре.

```
python mb.py env
```

**Подъём сервера идемпотентен, и это сделано нарочно.** Команда `serve`, кнопка «Поднять» в окне
и `morphbench.exe --start` делают одно и то же, сколько бы раз их ни повторили: сервера на этом
адресе нет — поднять, есть — отдать ему корень обзора и открыть страницу. Порт, занятый чужой
программой, отвергается словами, а не сбоем. Держать в голове, поднят сервер или нет, не нужно
ни человеку, ни программе.

```
python mb.py serve
```

```
python mb.py serve --status
```

```
python mb.py serve --stop
```

Окно ничего не считает само: каждая кнопка — один из этих же вызовов. Строка состояния говорит,
поднят ли сервер и кем, под MO2 ли окно и сервер, какой корень обзора и сколько под ним мешей.
Поле **Корень обзора** с кнопкой «…» и «Применить» меняет папку у поднятого сервера сразу
и запоминается в `morphbench.launcher.json` рядом с exe; под MO2 корень всегда `Data` игры,
и про него не спрашивают. Сервер, поднятый окном, останавливается вместе с ним; чужой — остаётся.

Ещё два довода exe стоит знать. `--root <папка>` задаёт корень обзора на один запуск, а голая
`<папка>` (или переменная `MORPHBENCH_HOME`) говорит, где лежит `mb.py`, если exe скопировали
в другое место. `--diag` не открывает окна вовсе: он пишет ответ `env --json` и кадр
в `morphbench.diag.json` и `morphbench.diag.png` рядом с exe — так проверяют VFS, не глядя
на экран, например запуском через мост MO2. Оговорка: меш, который `--diag` рисует, сейчас взят
жёстко — это запись обзора из одной конкретной сборки, а не то, что есть у тебя. На другой сборке
отвечает половина с JSON, а кадр может просто не появиться.

За кулисами окно передаёт `serve --parent <номер процесса>` — это велит серверу уйти вместе
с названным процессом. Окно, закрытое крестиком, останавливает сервер само; снятое **жёстко** —
аварийное завершение, «Снять задачу», выход из системы — не успевает, и без сторожа остался бы
невидимый сервер на устаревшей подмене MO2, к которому следующий запуск молча подключился бы.
Из консоли довод не нужен, и поведение там прежнее.

## Вне MO2: корень обзора надо назвать

Вне MO2 у корня обзора нет умолчания, и это намеренно: угадывать одну папку на диске, полном
мешей, бессмысленно. Корень называют ключом `--root`, полем на странице либо раз и навсегда —
ключом `catalogRoot` в настройках. Дальше обзор перечисляет то, что под ним лежит:

```
python mb.py catalog "D:\meshes"
```

Список пронумерован, и вместо пути можно назвать номер или кусок пути: `render --entry 3`,
`web --entry femalebody`. Ключ `--all` добавляет меши, у которых нет файла морфов.

## Настройки, которые трогают в первый час

`morphbench.json` создаётся рядом с `mb.py` при первом запуске из встроенных умолчаний, а ключи,
появившиеся в новой версии, дописываются в старый файл сами — так что видно всё, что вообще
настраивается.

| Ключ | Для чего | По умолчанию |
|---|---|---|
| `language` | `auto` — язык системы, либо папка из `locale\` | `auto` |
| `pynifly` | папка аддона PyNifly, когда она лежит не там, где обычно | пусто |
| `python` | путь к `python.exe` для `morphbench.exe`, когда тот его не находит | не пишется |
| `catalogRoot`, `catalogSubdirs` | корень обзора вне MO2 и подпапки, где искать | пусто, `["meshes"]` |
| `serveHost`, `servePort` | где отдаётся страница | `127.0.0.1`, `8767` |
| `baseShape` | имя кожи — части, за которой обязаны следовать оболочки | `body` |
| `skeletonFile` | имя файла скелета, который ищется в папке меша | `skeleton.nif` |
| `logFile`, `logLevel`, `logFileLevel` | журнал рядом с настройками и два его порога | `morphbench.log`, `info`, `debug` |

Пороги, которыми живут сами разборы, лежат в том же файле и объяснены там, где применяются:
растяжение и касание — `strainThreshold`, `budgetResolution`, `contactRadius`, `minContact` —
вместе с командами, которые их читают, в [cli.ru.md](cli.ru.md); запасы сфер, процентили, размер
связки и все числа SMP и CBPC — в [physics.ru.md](physics.ru.md).

## Пример на живом деле

Один настоящий проход, в том порядке, в котором он и шёл: тело своей расы в работе, шестнадцать
частей и двадцать восемь ползунков, со своим скелетом. Игра не понадобилась ни разу.

**1. Открыть и посмотреть, что там есть.**

```
python mb.py summary malebody_1.nif
```

Шестнадцать частей, файл морфов `TRIP` рядом с мешем, двадцать восемь ползунков. Пока хорошо:
морфы вообще собрались, а это первое, что отваливается молча.

**2. Спросить, не выходит ли что-нибудь за свой шар охвата.** У каждой части NIF записан шар,
по которому игра решает, видна ли часть. Считается он по телу в покое, и ползунки его
не расширяют — деталь, вытянутая морфом за шар, начинает пропадать от ракурса, и это та самая
классическая жалоба «мод мигает».

```
python mb.py bounds malebody_1.nif
```

| часть | в файле | тянется | перебор | чем | нужен |
|---|---|---|---|---|---|
| genitals | 9.3 | 45.6 | +388% | all=1 | 27.7 |
| fur_tailtip | 17.5 | 50.4 | +187% | worst | 33.5 |
| mouth | 10.7 | 21.8 | +104% | all=1 | 16.4 |
| eyes | 5.8 | 11.5 | +98% | all=1 | 9.5 |
| head | 32.1 | 47.7 | +49% | CLAWHeadEarSize=1 | 41.1 |
| body | 75.9 | 100.0 | +32% | all=1 | 87.1 |

Первая строка читается так: в файле шар 9.3, геометрия при худшем наборе ползунков уходит
от его центра на 45.6 — это на 388% дальше радиуса, — а накрыл бы её шар радиуса 27.7, с другим
центром. У исправных строк в конце просто нет пометки `<- расширить`. `--json` добавляет, какой
**одиночный** ползунок уводит дальше всех: здесь одного ползунка хватило, чтобы сломать
`genitals`, без помощи остальных двадцати семи. Вся таблица заняла около восьми секунд.

**3. Записать исправленные шары — в новый файл.**

```
python mb.py bounds malebody_1.nif --write malebody_1-fixed.nif
```

Исходник принадлежит чужому моду и не переписывается никогда; всё, кроме шаров, копируется байт
в байт. Шар только расширяется, но не сжимается — шар шире нужного могли расширить нарочно
под качающуюся физику, — а когда сжать действительно надо, для этого есть `--shrink`. Без файла
морфов рядом запись отказывает наотрез: тогда «нужный» шар — это шар покоя, и писать нечего.

**4. Посмотреть на предмет глазами** — убедиться, что числа описывают именно то, о чём думаешь.

```
python mb.py web malebody_1.nif --skeleton skeleton.nif --out check.html
```

**5. Спросить, как сидят капсулы столкновений.** Удары и прикосновения игра считает
по невидимым капсулам из файла скелета, по одной на кость, — а не по коже.

```
python mb.py colliders malebody_1.nif --skeleton skeleton.nif --clearance
```

Голова ответила «снаружи 66% кожи» — две трети её поверхности лежат вне капсулы, которая должна
её изображать, — а стопа 98%. Одна капсула верна для вытянутого: бедро, голень, предплечье.
Голова и стопа почти одинаковы во все стороны, и одной капсулой не накрываются.

**6. Посадить капсулы по коже.** Этим двум — связкой, а не одной капсулой:

```
python mb.py fit malebody_1.nif --skeleton skeleton.nif --find Head --bundle 14 --split kmeans --save skeleton-fitted.nif
```

```
python mb.py fit malebody_1.nif --skeleton skeleton.nif --find "L Foot" --bundle 3 --split axis --save skeleton-fitted.nif
```

`--split axis` режет кожу ломтиками вдоль кости, что подходит конечностям; `kmeans` режет
сгустками по близости, и тогда череп, морда и челюсти находятся сами. Тело в скелете остаётся
одним телом с теми же шарнирами — меняется только его форма. Повтор шага 5 против записанного
файла дал 66% → 28% у головы и 98% → 36% у стопы. Ключ `--ppb` печатает ту же посадку строками
для `PPB_tuning.txt`, который Precision Physic Bodies перечитывает примерно раз в секунду прямо
во время игры.

**7. Проверить то, что должно качаться.** Уши, хвосты и грудь качают не капсулы куклы, а вторая
физика — Faster HDT-SMP или CBPC, — и качает она **кости**, только там, где к ним привязана кожа.

```
python mb.py chains malebody_1.nif --skeleton skeleton.nif
```

По каждому звену видно, сколько вершин каких частей оно держит. Звено без кожи в начале цепочки —
опора (так устроен 3BBB: `Breast00` ведёт анимация), посреди — шарнир, в конце — хвост, который
отбрасывается. «Кожи нет ни на одном звене» — вот это настоящий обрыв: движку нечего двигать.
Одну кость двум движкам отдавать нельзя, поэтому каждая цепочка отдана одному из них —
`chainEngines` в настройках либо на один запуск `--assign tail=cbpc,ear=smp`.

**8. Проверить файл настроек, который собираешься выпустить.** Оба движка молчат об ошибке:
опечатка в имени кости означает, что ничего не качается, и нигде ни слова.

```
python mb.py physics malebody_1.nif --skeleton skeleton.nif --engine smp --check ears.xml
```

Чистый файл отвечает, что ссылается только на то, что есть, и выходит с кодом 0. Плохой печатает
по строке на находку — род, имя, где, в чём дело — и выходит с кодом 3, за которым и должен
следить сборочный скрипт.

Вот и весь проход. Он нашёл деталь, которая моргала бы, капсулы, промахивающиеся мимо тела
большей частью его поверхности, и поймал бы опечатку в имени кости до того, как игра вообще
загрузится, — из папки с файлами, ни разу не запустив Skyrim.

## Что пока шероховато

- Окно запуска само не находит папку `python\`, вложенную в архив выпуска; на машине без
  установленного Python на неё надо указать переменной `MORPHBENCH_PYTHON` (см. выше).
- `--diag` рисует жёстко заданную запись обзора, а не что-то из твоей сборки, поэтому половина
  с PNG может оказаться пустой, пока половина с JSON отвечает.
- Страница одним файлом не делает ни одного `fetch`, не знает модулей и не ссылается наружу:
  она рассчитана открываться прямо с диска по `file://`. Это замысел, а не недоделка, и браузер,
  отказывающий локальным файлам, — повод проверить его настройки, а не страницу.

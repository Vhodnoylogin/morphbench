# Сборка и выпуск Morphbench

Эта ветка разработки сохраняет отдельный эксперимент **Morphbench Slots 0.8.0-slots.1**
поверх выпущенных Application 0.8.7 и Launcher v3. Экспериментальные сборки остаются
отдельно от основной линии на странице Nexus Mods 194795. Обозначения эксперимента
принадлежат исходникам и переводам Application; перечни выпущенных Runtime неизменяемы.
Опорные меши и скелеты не входят в архив. Проверка комплекта возможна без браузера;
недоступная визуальная проверка остаётся отмеченной как недоступная.

Команды выполняются из корня репозитория. Рабочий код — `src/main/`, тесты и пробники —
`src/test/`, результаты — игнорируемый `target/` или отдельная папка сборки. Исходники
выпуска находятся в `main`, незавершённая Application — в `experimental/body-slots`.
Незавершённые функции не включаются в выпуск ланчера.

## Нативный хост и совместимость

Команда `src\main\launcher\build.cmd` использует установленный компилятор .NET Framework;
Pillow создаёт значок. Результат — `target/launcher/morphbench.exe`. Launcher v3 имеет версию сборки 3.0.0.0 и минимальный протокол хоста 1.
[Контракт](launcher-protocol.ru.md) оставляет C# только фиксированный запуск комплектного
Python/shim, экранирование аргументов и ожидание/код выхода. Для работы с исходниками
разместите рядом python/ и vendor/ закреплённого Runtime и launcher/mb.py из Application;
задайте MORPHBENCH_APP абсолютным src/main. Один EXE больше не ищет системный Python.
Параметры пользователя сохранены в shim/контроллере. Адаптеры v1/v2 остаются доступны.
Runtime v3 также требует launcherHostProtocol 1; сначала обновите App.

`runtime-lock.json` — точная зависимость **сборки**, не правило совместимости при запуске.
Application схемы 2 проверяет API/ABI: совместимый будущий Runtime с другой версией и
хешем не требует пересборки App. Целостность Runtime проверяется по собственному перечню.
Старые App схемы 1 сохраняют точную привязку.

## Повторное использование закреплённого пакета

Скачайте точный архив из `src/main/runtime-lock.json`, проверьте SHA256 и распакуйте
`root/Morphbench/launcher`. Учтённые файлы не меняйте. Упаковка:

```text
python release.py --package runtime --runtime-from <распакованный-launcher> --runtime-version 3 --out <результат>
python release.py --package application --runtime <распакованный-launcher>/runtime-manifest.json --version 0.8.7 --out <результат>
```

Сборщик сравнивает ID, contentHash и Python с закреплением исходников. Оба архива имеют
`root/Morphbench/`. Общие shim/переводы принадлежат App. Application не содержит нативных
бинарников, проверяет API/ABI. Для прежних плоских установок есть `--layout flat`;
обычный выпуск структурированный. Менять структуру обновлением поверх запрещено.

Для GitHub объедините проверенные структурированные компоненты в одну загрузку:

```text
python release.py --package combined --runtime-from <runtime.zip> --application-from <application.zip> --out <результат>
```

Получится `morphbench-<версия-Application>-win64.zip` с обеими частями внутри
`root/Morphbench/`. Сборщик проверяет перечни и совместимость, сохраняет манифесты и
байты файлов; общие shim/переводы берёт из Application. Компилятор и загрузка зависимостей
не нужны. На Nexus остаются два отдельных файла. Уже опубликованные зеркала компонентов,
на которые ссылаются неизменяемые закрепления и запросы проверки, сохраняются;
пользователям GitHub предлагается объединённый ZIP.

## Создание нового Runtime

Новый EXE, интерпретатор или нативная зависимость требуют нового ID, проверки и загрузки
на модерацию. Не заменяйте опубликованный ID/архив. Подготовьте новую полную заготовку:
новый EXE, `python/`, `vendor/`, лицензии/уведомления/зависимости, `manifest.json` с точным
Python. Старую заготовку сохраните. Сначала зафиксируйте исходники, затем:

```text
python release.py --package runtime --new-runtime --runtime-from <новая-заготовка> --runtime-version <новая-версия-runtime> --source-commit <точный-40-hex-коммит> --out <результат>
```

`--new-runtime` запрещает ID v1 и ID текущего закрепления, требует заготовку без манифеста
Runtime. Создаёт контракт совместимости, удаляет известные служебные файлы, проверяет
происхождение DLL перед заявлением о версии автора и сверяет готовый ZIP с перечнем
и общим overlay App. После проверки сохраните новые хеши, Python, URL и коммит нативных
исходников в `runtime-lock.json`. Зафиксируйте закрепление и соберите App с точного коммита.
Последующее повторное использование Runtime обязано соответствовать закреплению.

`--source-commit` по умолчанию — проверенный Git HEAD. Ссылки исходников и сборки в
уведомлениях указывают неизменяемый коммит. Не приписывайте старому EXE новые исходники.
Не меняйте байты проверенного пакета: изменение создаёт нового кандидата.

## Только рабочие файлы в пользовательских архивах

Сохраняйте исполняемые зависимости, Python/JS, ресурсы, манифесты, лицензии/уведомления,
краткую установку и доступ к исходникам. Упакованные README — отдельные краткие инструкции;
`SOURCE.md` указывает точные исходники App. Дополнительные C#/C++, компиляторы, сборочные
рецепты, тесты, stubs, кэши и исходники встроенного значка остаются в GitHub. Руководства
`building` и `launcher-protocol` в Application не выбираются.

Нужный байткод stdlib, расширения и лицензии/SBOM wheel сохраняются. Не удаляйте импорт
только из-за слова test в имени. Очистка нового Runtime проверяется реальными импортами
и файловыми операциями; один манифест не доказывает минимальность и работоспособность.
Полную заготовку можно собрать через `--package full` с `dependencies.json`: нужен
Windows x64 Python той же major/minor, собранный EXE и указанная папка PyNifly.

Лицензии и происхождение Python, NumPy, Pillow и PyNifly остаются в уведомлениях Runtime.
Python-файлы PyNifly используют V28.1.0, коммит `934fbbfbb41b63ed636d44afa957ec98d7fb0803`.
Новая DLL собирает эту оболочку с Nifly `8a57cdef83aa97a976b4e317aa5cc2a1fa7fd88d`;
компилятор и статическая CRT закреплены в `dependencies.json`. Это новая сборка с известными
исходниками, а не воспроизведение прежней DLL из v1. Сборка и отдельный архив исходников:

```text
python src/main/build-nifly.py --out <нативная-сборка>
```

Рецепт получает точные коммиты, создаёт вариант проекта со статической CRT и записывает
реальный хеш. Отдельный `morphbench-nifly-corresponding-source.zip` содержит оба исходника,
лицензии, метаданные и рецепт; сборка не требует получения их Git-репозиториев. Это
разработческий архив GitHub; внутри Runtime его нет. Уведомления half/Miniball идут с DLL.
Минимальность не отменяет предоставления соответствующих исходников.

Это C/C++-исходники зависимости, а не дубликат исходников Morphbench. Git Morphbench
хранит закрепления и рецепт сборки, но не сами сторонние деревья исходников. Для работы
достаточно полного ZIP с GitHub либо двух файлов Nexus; архив исходников нужен для
пересборки и аудита DLL и отдельно сохраняет доступ к соответствующим ей исходникам.

Исходники и лицензии автора: [PyNifly, коммит оболочки](https://github.com/BadDogSkyrim/PyNifly/tree/934fbbfbb41b63ed636d44afa957ec98d7fb0803)
и [Nifly, коммит библиотеки](https://github.com/BadDogSkyrim/nifly/tree/8a57cdef83aa97a976b4e317aa5cc2a1fa7fd88d).
Оба проекта используют GPLv3; лицензии и авторские уведомления сохраняются. Ссылка
на сторонние исходники допустима при равноценном доступе к соответствующим исходникам
и сохранении их доступности, пока распространяется бинарник; см.
[FAQ GNU](https://www.gnu.org/licenses/gpl-faq.en.html#SourceAndBinaryOnDifferentSites).
Наш необязательный снимок дополнительно содержит использованный рецепт сборки DLL
и сохраняет точные входные файлы независимо от доступности авторских репозиториев.

## Проверка и публикация

Выполните `python src/test/run.py`. Нативные проверки компилируют минимальный C#-хост:
аргументы/рабочая директория/окружение, фиксированный Python, ошибки запуска, ожидание
и коды выхода без показа окон. Проверки Python-сеанса и скрытого Win32-окна охватывают
владение сервером, гонки закрытия, смерть/повторное использование PID и элементы управления.
Проверьте собранную установку
встроенным Python: импорты, CLI/HTTP, окно, NIF/TRI/PNG, адаптеры прежних v1/v2, переход
на v3 после обновления App, повторные обновления и сохранность настроек/плагинов.
Активны Морфы и Коллайдеры; Физика и Body Slots остаются отключены. Перед публикацией
зафиксируйте хеши окончательных архивов и соответствующие коммиты. Фактическая работа MO2/usvfs проверяется отдельно;
синтетический поиск её не доказывает.

Публикуйте исходники в `main`, архивы — в GitHub/Nexus; историю сохраняйте. В Nexus имя
файла описательное, версия — отдельным полем. Application — Primary, Launcher — другой
Main, Root Builder необязателен. Загрузка, карантин и снятие карантина — отдельные факты.
Новый нативный архив может попасть в карантин. Обычные изменения App остаются вне
замороженного пакета, чтобы не перезаливать неизменные EXE и зависимости.

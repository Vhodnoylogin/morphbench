# Совместимость Launcher и Application

Launcher v2 — небольшой Windows-хост. В нативных байтах остаются окно, управление
процессами, ограниченное чтение каналов и отмена. Application владеет Python-bootstrap,
поиском установки, настройками, переводами и адаптерами сервера. Логика мешей, морфов
и плагинов не должна попадать в EXE.

## Три независимые версии

| Контракт | Текущее значение | Когда нужен новый нативный пакет |
|---|---|---|
| Совместимость Runtime/Application | API 1, `cp312-win_amd64` | действительно меняются нативные зависимости или интерпретатор |
| Нативный bootstrap и адаптер сервера | протокол 1 | хосту нужна новая нативная возможность |
| API браузерных плагинов | API 1 | само по себе не требует нового EXE; принадлежит Application |

Манифест Application схемы 2 содержит `requiresRuntime` с `apiVersion` и `pythonAbi`.
Манифест Runtime объявляет `applicationApi`, `pythonAbi` и собственный перечень хешей.
Совпадение API/ABI допускает разные версии и хеши Runtime. Целостность каждого файла
по-прежнему проверяется, как и точный выбранный интерпретатор. Хеш выявляет изменение
файла, но не является подписью подлинности.

Единственный старый Runtime v1 без контракта распознаётся по зафиксированной паре
идентификатор/хеш. Старые манифесты Application схемы 1 сохраняют смысл точной привязки;
их значение не переопределяется. Application 0.8.6 поддерживает v1 и v2; перед v2 нужно
обновить Application 0.8.5. Одноразовый переход новым установщиком описан в
[инструкции установки](install-layout.ru.md).

## Протокол нативного bootstrap 1

Пути `launcher/mb.py` и `launcher/python/python.exe` — стабильные точки входа EXE.
Оба пакета содержат одинаковый shim, принадлежащий Application; при конфликте выигрывает
Application. EXE вызывает:

```text
python.exe mb.py --launcher-context --protocol 1
```

Shim использует только стандартную библиотеку: не импортирует App, не запускает сервер,
не пишет настройки и не проверяет все зависимости ради поиска установки. Сначала
используется абсолютный `MORPHBENCH_APP`, затем соседняя App, затем единственная полная
установка в корне игры. Отсутствие, неверная подсказка и неоднозначность дают отказ.
Пути остаются лексическими для MO2.

Успех: код 0 и один JSON-объект в stdout. Диагностика идёт в stderr. Обязательные поля:
`protocolVersion: 1`, абсолютные `appHome`, `settingsHome`, `localeHome` (сама папка locale),
объект `settings`, относительный префикс `serverApi` с завершающим `/`, строки CLI
`statusArgs` и `startArgs`. Неизвестные поля игнорируются; смысл известных сохраняется.
Необязательное `environmentArgs` адаптирует диагностику; по умолчанию `env --json`.
В `settings` допускаются язык и положительные ограниченные параметры
`launcherCliTimeoutMs`, `launcherHttpTimeoutMs`, `launcherStopWaitMs`,
`launcherLogMaxChars`. При отсутствии или ошибке применяются значения bootstrap:
30000, 30000, 5000 мс и 200000 символов. Таймаут охватывает завершение процесса и EOF каналов.

Application может расширить ответ или добавить адаптер другого протокола, сохраняя
протокол 1 для опубликованного v2. Неподдерживаемая версия запроса завершается ненулевым
кодом без запуска App. Новые схемы папок, настройки и серверные изменения реализуются
в shim/адаптере, а не в нативном поиске. Это доверенный локальный код, не подписанный канал обновлений.

Выданные команды CLI сохраняют флаги: EXE добавляет правильно экранированные `--root`
и `--parent`. `serve --status --json` возвращает существующие словари состояния, URL
и окружения; обычный `serve` идемпотентен. Никакие вычисления не доступны исключительно окну.

## Адаптер сервера 1

Префикс — `api/launcher/v1/`. GET-окончания: `environment`, `root` (необязательный
URL-кодированный параметр `root`) и `shutdown`. Поля JSON, коды ответа, проверки чужого
origin и идентификатор Server `morphbench/` сохраняют смысл существующих `/api/*`.
Публичные маршруты остаются доступны. Внутренний API может меняться, пока эти три
адаптера сохраняют контракт EXE.

Автоматическое закрытие владельца передаёт `shutdown?pid=<PID дочернего Python>`.
Адаптер возвращает 409 без остановки, если PID не совпадает с собственным. Без `pid`
сохраняется ручной Stop. Это защищает другой сервер на том же порту, если идемпотентный
или завершившийся дочерний процесс уже ему не принадлежит. Проверка входит в протокол 1.

Закрытие отменяет нативные операции и исключает callbacks в уничтоженное окно. Останавливается
только сервер этого окна; независимо запущенный сервер продолжает работать. Python-наблюдатель
освобождает порт и при смерти ланчера во время начальной загрузки.

## Граница релиза

Опубликованный перечень Runtime неизменяем. Исправление EXE, интерпретатора или зависимостей
получает новый ID Runtime и отдельную проверку. Совместимый Runtime не требует пересборки App.
Обновления Application не содержат EXE/DLL/PYD, сохраняют настройки и плагины. Разделение
позволяет не перезаливать неизменные нативные файлы с каждым обновлением App; новый нативный
архив всё равно может потребовать проверки Nexus.

Нельзя обещать, что v2 никогда не понадобится заменить: нативная ошибка, смена ABI
интерпретатора или новая нативная возможность могут потребовать этого. Обычная разработка
Application не должна затрагивать EXE.
